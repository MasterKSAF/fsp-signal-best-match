# Проверить решение самостоятельно

Общий **Demo** остаётся обзором подготовленных синтетических примеров. Для независимой проверки экзамена используйте два отдельных набора: в каждом свой кандидат, работодатель и компания. Учётные данные выдаются локальным инструментом, не находятся в исходниках, публичном архиве или ответах API.

## Подготовка локального стенда

1. Разверните отдельную локальную копию API/БД по инструкции ниже. Примените все миграции, включая `0006_assessment_purpose`, `0007_reviewer_scope`, `0008_resume_pool_digest` и `0009_microtask_resume`. При необходимости заполните только общий обзорный Demo штатным seed. Это инструкция к исходникам 0.6; новый чистый запуск запечатанного архива пока PENDING.
2. Задайте `DATABASE_URL` **своей именованной изолированной БД**, `DEMO_MODE=true` и `SIGNAL_REVIEWER_PROFILE=isolated-local-review`. Инструмент откажется работать с сетевой БД, рабочим портом БД 55433, БД `signal`/`postgres` или рабочим API 4310–4312.
3. Укажите собственный локальный API, точное имя БД и абсолютный путь к **новому** JSON за пределами папки проекта. Полный Docker-рецепт ниже создаёт эти переменные и один раз вызывает provisioning; не выполняйте `create` повторно для того же файла.

Имя/порты в рецепте относятся только к изолированному стенду. Инструмент выводит путь и количество, **не пароли и не адреса**. Существующий файл не перезаписывается. Закройте доступ к нему другим пользователям компьютера и передайте каждому проверяющему только его пару. Файл содержит случайные уникальные пароли, ID своих записей и два разных серверных `reviewScopeId`; в конкурсный архив он не входит.

Это контролируемые синтетические фикстуры: локальный администратор создаёт их с подтверждённой почтой и помеченными фикстурными согласиями. Это **не** тест реальной доставки подтверждения и **не** обход публичной регистрации. При обычной регистрации подтверждение адреса по локальной Mailpit/SMTP и принятие согласий обязательны; JSON/заголовок с `demoMode`, `reviewMode` или scope не меняет обычную учётную запись.

## Полный отдельный стенд с Docker

Из корня **новой распакованной копии** исходников в PowerShell 7. Нужны Node.js 24, pnpm 11.25.0 и Docker Desktop. Этот пример использует собственные 4334/55441/8034; при занятых портах он останавливается, не завершает чужие процессы. Пароли создаются случайно в памяти текущего PowerShell и не выводятся. Файл доступа находится за пределами распакованной копии.

```powershell
foreach ($port in 4334,55441,8034) {
  if (Get-NetTCPConnection -LocalPort $port -State Listen -ErrorAction SilentlyContinue) {
    throw "Port $port is occupied; choose another isolated stand"
  }
}
$reviewRun = [guid]::NewGuid().ToString('N').Substring(0,8)
$reviewProject = "signal-review-$reviewRun"
$reviewDatabase = "signal_review_$reviewRun"
$reviewPrivate = Join-Path ([Environment]::GetFolderPath('UserProfile')) ".signal-reviewer-private/$reviewRun"
New-Item -ItemType Directory -Path $reviewPrivate | Out-Null
$reviewOverride = Join-Path $reviewPrivate 'review.compose.yaml'
$reviewAccounts = Join-Path $reviewPrivate 'reviewers.json'
$env:POSTGRES_PASSWORD = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(24)).ToLowerInvariant()
$env:VERIFICATION_TOKEN_SECRET = [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(32)).ToLowerInvariant()
$env:SIGNAL_HTTP_PORT = '4334'
$env:SIGNAL_DB_PORT = '55441'
$env:SIGNAL_MAIL_PORT = '8034'
$env:DEMO_MODE = 'true'
$env:SIGNAL_REVIEWER_PROFILE = 'isolated-local-review'
$env:DATABASE_URL = "postgresql://signal:$($env:POSTGRES_PASSWORD)@127.0.0.1:55441/$reviewDatabase"
@'
services:
  db:
    environment:
      POSTGRES_DB: __REVIEW_DATABASE__
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U signal -d __REVIEW_DATABASE__"]
  app:
    environment:
      DATABASE_URL: postgresql://signal:${POSTGRES_PASSWORD}@db:5432/__REVIEW_DATABASE__
      PUBLIC_URL: http://127.0.0.1:4334
'@.Replace('__REVIEW_DATABASE__',$reviewDatabase) | Set-Content -LiteralPath $reviewOverride -Encoding utf8
$reviewCompose = @('compose','-p',$reviewProject,'-f',(Join-Path (Get-Location) 'compose.yaml'),'-f',$reviewOverride,'--profile','full')
pnpm install --frozen-lockfile
if ($LASTEXITCODE -ne 0) { throw 'Dependency install failed' }
docker @reviewCompose up --build -d
if ($LASTEXITCODE -ne 0) { throw 'Review stand launch failed' }
```

Дождитесь `status: ok` у `http://127.0.0.1:4334/api/healthz`. Контейнер применяет миграции и seed при старте; ошибка видна через `docker @reviewCompose logs app`. Затем, в **той же PowerShell-сессии**, создайте доступы:

```powershell
node --import tsx scripts/provision-reviewers.ts --mode create --origin http://127.0.0.1:4334 --database $reviewDatabase --private-file $reviewAccounts
if ($LASTEXITCODE -ne 0) { throw 'Reviewer provisioning failed' }
```

Откройте `http://127.0.0.1:4334` и `http://localhost:4334` в двух независимых браузерных профилях. Данные каждой пары смотрите только в собственном private JSON. Для обычной регистрации почта доступна в `http://127.0.0.1:8034`; локальная Mailpit принимает письма без внешнего сервиса. Штатный Compose использует Mailpit HTTP transport. Реальный SMTP выбирается отдельной конфигурацией и не объявляется проверенным этим примером.

После ручной проверки можно удалить **только этот отдельный проект** командой `docker @reviewCompose down --volumes`. Она уничтожит тестовое состояние этого стенда, поэтому не используйте её для рабочего проекта. Сохранённый private JSON с паролями в конкурсный комплект не копируется. Новая сессия PowerShell потребует восстановить именно свои project/database/override параметры и среду; пароль из working `.env` подставлять вместо созданного здесь нельзя.

## Прохождение проверки

1. Войдите обычной формой логина из своей пары, не кнопкой общего Demo. Два проверяющих могут работать в независимых профилях браузера; для приведённого отдельного Docker-стенда подходят `127.0.0.1:4334` и `localhost:4334` с отдельными cookie. Рабочий стенд на 4314 этим рецептом не используется. В режиме проверки интерфейс показывает синтетический статус.
2. Кандидат начинает с закрытого пустого резюме, без категории, попытки, истории ФСП и готовых ответов. Выберите специализацию, заполните первичный опрос, явно подтвердите уровень и начните квалификационную проверку Signal. Сервер выдаёт реальные текущие задания и оценивает **ваши** ответы. Никакой автоматической успешной оценки нет.
3. Сохраните ответ, выйдите и войдите снова. Откроется собственная попытка с собственным черновиком. Другой набор не видит ваш черновик или попытку. После отправки посмотрите результат и его объяснение. Неудачная попытка не присваивает категорию; штатные интервалы повторов и изменения уровня действуют и здесь.
4. Для просмотра со стороны своей компании отдельно включите видимость резюме и согласие на каталог/подбор. Работодатель видит только кандидата своей пары; при пустом/закрытом резюме список пуст. Для подбора дополнительно нужны обычные условия допуска и подтверждённая категория. Готовые общие Demo-кандидаты и другая пара в этот пул не попадают.
5. При повторном входе остаются те же записи. Инструмент `--mode status` проверяет принадлежность записей, ничего не сбрасывая. Новый запуск `create` с другим приватным файлом создаёт новые пары, а не снимает cooldown существующих. Публичного reset endpoint нет.

## Новые сценарии 0.6

После собственной квалификации откройте «Мои подтверждения»: один исходный критерий показывается один раз с прежней датой и версией. Скопируйте документ и выберите копию — применимые навыки сохранят источник. Затем выберите другое IT-направление: реестр покажет причину неприменения, а весь прежний грейд не перейдёт в другую программу. Уровень отдельного критерия не является грейдом полной программы. Не нужно повторно решать тот же экзамен только ради копии резюме; действующие ограничения повторов сохраняются.

В собственных полях должности, проектной роли, предметной области и личных навыков попробуйте подсказку и авторское значение; сохраните, перечитайте после повторного входа. Эти значения не становятся подтверждёнными навыками. Выбор IT-направления остаётся закрытым набором реально поддерживаемых программ.

Работодатель своей пары может создать задание компании и выбрать конкретное допустимое резюме кандидата. После отправки проверьте, что кандидат видит исходный документ, условия и рубрику. Смена основного документа не переносит предложение. Скрытие, удаление, смена направления или отзыв согласия исходного документа прекращают новые действия; восстановление видимости само не возрождает отозванную подписку. Оценка компании не присваивает грейд Signal. Прежняя практика без сохранённого документа обозначается ограничением `legacy_unbound`.

Это проверочный маршрут, не утверждение, что проверяющие или реальные люди уже его прошли. Фактический новый браузерный протокол добавляется отдельно.

## Серверная изоляция

`demoMode=true` означает **синтетический пул**, а не право пропустить экзамен. `reviewScopeId=null` у обзорного Demo; UUID каждой пары у проверяющих. Ordinary имеет `demoMode=false, reviewScopeId=null`. Все чужие выборки требуют совпадения обоих полей; сервер берёт их из подтверждённой учётной записи, не из клиентского запроса. Только `overviewDemo = demoMode && reviewScopeId === null` сохраняет старые обзорные послабления. У проверяющих `overviewDemo=false`: первичный опрос, ограничения, сохранение, серверная оценка и владение попыткой обычные. Права модератора не выдаются.

Сессия фиксирует scope при создании и аннулируется, если администратор изменит принадлежность аккаунта. `/auth/demo-session` открывает только исходные обзорные аккаунты. `demo:reset` очищает только обзорный null-scope; проверяющих и ordinary пользователей сохраняет. ФСП-флаг не заполняется инструментом. Синтетические достижения проверяющих не входят в обычный пул.

## Проверки и точная уборка

Модульные проверки: `node --import tsx --test tests/reviewer-scope.test.ts`. Короткий API-сценарий создаёт **свои новые** четыре записи, проверяет два отдельных экзамена, чужие ID, save/relogin, неуспешную реальную оценку, cooldown, две компании и отсутствие answer keys. Он использует заведомо неверный текст, **не** читает oracle и **не** доказывает валидность категории на людях.

```powershell
$env:API_ORIGIN = 'http://127.0.0.1:4334'
$env:REVIEWER_DATABASE_NAME = $reviewDatabase
$env:SIGNAL_REVIEWER_HTTP_PROBE = 'true'
node --import tsx scripts/reviewer-http-integration.ts
```

Новый фактический результат записывается в `outputs/verification/reviewer-http-2026-10-06.json`; старый при повторе сохраняется в history по SHA. До запуска это лишь сценарий, не PASS. Проверка не нагружает стенд и удаляет только свои четыре аккаунта по приватному manifest. Рабочие пары проверяющих не используются. Для ручного удаления своей пары используйте `provision-reviewers.ts --mode remove` с теми же тремя параметрами: инструмент сначала проверяет точные ID/email/scope/роли/имя изолированной БД. Он не reseed/reset всей БД. Приватный файл остаётся локальным журналом. Старые проверки версии 0.4.1 не являются приёмкой этой функции.
