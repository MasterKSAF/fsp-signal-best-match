# Резюме и происхождение квалификации

Актуальный этап: несколько резюме и каталог, 6 октября 2026 года. Это новая версия поведения; результаты приёмки 0.4.1 не доказывают её качество.

## Модель

`signal_users` — аккаунт; `signal_candidate_profiles` — общая идентичность, контакты, аватар и исходная историческая сводка. Профессиональные поля профиля остаются **проекцией основного резюме для совместимости**, а не источником квалификации. `signal_candidate_resumes.id` — стабильный ID; `user_id` больше не уникален. `revision` изменяется при содержательном редактировании и изменении квалификации. Удаление — `deleted_at`, без удаления попыток. Основное резюме имеет частичный уникальный индекс, но не бонус в рейтинге.

Попытки принадлежат кандидату. Новая попытка сохраняет `resume_id`, `resume_revision`, `resume_specialization`, `program_version`. Изменение или удаление цели не переписывает историю и не воскрешает резюме. Отклик/приглашение сохраняет `resume_id` и профессиональный `resume_snapshot`; снимок исключает имя, аватар, телефон и email. Снимок не является разрешением читать скрытое резюме или контакты.

Все активные, скрытые и незавершённые резюме входят в лимит пяти. Скрытие место не освобождает, мягкое удаление освобождает. Создание и проверки лимита выполняются под `pg_advisory_xact_lock(3306,user_id)`; DB-trigger проверяет тот же лимит и роль аккаунта. Основное автоматически назначается при первом создании и замене удалённого основного. Повреждённая запись основного не заменяется случайной строкой.

## Применимость и грейд

Чистая функция `getResumeQualification` использует неизменные завершённые попытки и набор отозванных ID. Поддерживаются реальные сохранённые программы Backend / Python и Frontend / TypeScript с проверкой полной структуры шести критериев и зарегистрированных версий (историческая Backend v4; managed Backend v5/v6 и Frontend v1/v2). Версия нового контекста должна совпасть с сохранённой программой. Новая неизвестная версия не получает автоматическую совместимость.

Навык подтверждается полностью решённым критерием и явным соответствием **семейства критерия и канонического навыка**. Используются контролируемые синонимы из `skill-catalog`. Произвольный текст или совпадение названия навыка в другой программе не являются доказательством. В существующих двух программах нет общего проверяемого семейства: перенос Backend → Frontend не выполняется. Для будущего общего SQL нужна отдельная проверенная матрица содержательной совместимости.

Актуальные применимые результаты доступны всем резюме этой специализации независимо от исходного `resume_id`. Дата, ID и версия исходной попытки сохраняются. Один канонический навык учитывается один раз: выбирается доказательство более высокого проверенного уровня, затем более поздняя дата и стабильный ID. Частичные результаты могут подтверждать отдельные полностью решённые критерии, но **не складываются в новый грейд**. Грейд требует одной полной успешной программы с её обязательными критичными критериями и прежними порогами (Junior 67, Middle/Senior 83). Выбирается наивысший заработанный уровень, затем последняя успешная попытка этого уровня. Самооценка и рекомендация анкеты его не повышают.

Старый итог без полной программы сохраняется как `legacyQualification` с первоначальной датой и ограничением происхождения. Из общего балла не изобретаются новые отдельные критерии, версии или достижения. Полная отмена связанной исходной попытки отменяет и этот итог; несвязанная историческая сводка не получает ложной связи с случайной попыткой. Общая сводка аккаунта остаётся после удаления первого резюме и применима только к исходной специализации.

`recomputeCandidateResumes` пересчитывает все неудалённые резюме при новой проверке, отзыве и изменении специализации и обновляет проекцию основного. Контекст попытки и cooldown остаются на уровне кандидата/семейства программы. Новые резюме не создают новые попытки и не снимают ограничения.

## API

Все ответы кандидата и PDF используют `Cache-Control: no-store, private`.

| Операция | Контракт |
|---|---|
| `GET /api/me/resumes` | `{resumes, count, limit:5}` с отдельной квалификацией |
| `POST /api/me/resumes` | `{title,specialization,copyFromId?}`; 409 `RESUME_LIMIT` при пяти |
| `POST /api/me/resumes/:id/copy` | `{title?}`; копирует выбранное своё резюме через тот же атомарный лимит, закрыто для размещения; имя по умолчанию «… — копия» |
| `GET /api/me/resumes/:id` | Только владелец и неудалённое резюме |
| `PUT /api/me/resumes/:id` | Полное содержимое `SaveResumeSchema`, необязательная `revision`; профессиональные поля не сбрасываются |
| `PATCH /api/me/resumes/:id` | `title`, `visibility`, `consentMatching`, `consentCatalog`, `readyForOffers`, необязательная `revision` |
| `POST /api/me/resumes/:id/primary` | Назначение основного под блокировкой |
| `DELETE /api/me/resumes/:id` | Мягкое удаление; исходные общие попытки сохраняются |
| `GET /api/me/resumes/:id/pdf` | PDF выбранного резюме; заголовки ID и revision; контакты не принимаются PDF-renderer |
| `POST /api/me/avatar` | `{dataUrl}`: PNG/JPEG/WebP, до 2 MiB декодированных bytes, raster signature; SVG запрещён |
| `DELETE /api/me/avatar` | Удаление общего аватара |

Чужой или удалённый ID возвращает 404 без раскрытия владельца. Проверка переданной `revision` отклоняет устаревшее редактирование с 409 `RESUME_REVISION_CONFLICT`. Старые `/me/resume` и `/me/resume/pdf` поддерживают `?resumeId=<id>`; без ID используют только основное. Новые потребители передают ID явно.

Новые/скопированные резюме закрыты, `consentCatalog=false`, `consentMatching=false`; старая миграция сохраняет прежнее согласие на подбор, но не выдаёт согласие на каталог. Готовность к предложениям задаётся отдельно кандидатом. Имя и аватар не выводятся работодателю в pseudonymous режиме; фото не влияет на квалификацию.

## Миграция и восстановление

`0004_multi_resume.sql` добавляет поля и стабильный serial ID, переносит точные прежние профессиональные значения в первое резюме. Кандидат без старой строки резюме получает первую строку; работодатель не получает резюме. Содержание JSON и история анкеты остаются без изменения. Долговечная таблица `signal_resume_migration_state` предотвращает повторный backfill, в том числе после удаления перенесённого резюме.

Контекст старой попытки определяется сохранённым program/oracle metadata. Связь с первым резюме добавляется лишь при совпадении исходной специализации программы; неизвестный контекст остаётся неизвестным. Старые связи приглашения/отклика сохраняются. Исторический `resume_snapshot` остаётся NULL: точная ревизия на момент прежнего действия не восстанавливается из текущего резюме.

Перед применением: создать отдельный `pg_dump --format=custom --file=<backup> <connection>` с проверкой его размера/читаемости; восстановить его в отдельную БД, выполнить обычный `db:migrate`, повторно выполнить SQL 0004 и проверить отсутствие дублей/изменения данных. Затем пересчитать квалификацию всех кандидатов и пройти сценарии нового этапа. Только после проверки переключать runtime; реальные пользовательские строки не сбрасываются.

Откат выполняется на остановленном runtime восстановлением проверенной **полной резервной копии** через `pg_restore` в явно выбранную БД, затем возвращением предыдущих совместимых binaries. Не использовать частичное удаление столбцов как восстановление: оно потеряет новые резюме и связи. Зафиксированные архивы предыдущей сдачи не перезаписываются.
