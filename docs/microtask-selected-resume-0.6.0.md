# Практика компании по выбранному резюме — 0.6.0

## Поведение

Компания выбирает конкретное доступное резюме человека. Основное резюме не является источником допуска к практике: видимое подтверждённое вторичное резюме подходит, даже если основное скрыто или не подтверждено. Необходимы согласие на подбор, добровольное включение практики, тот же серверный пул и отсутствие блокировки компании. Шаблон должен явно указывать `Backend / Python` либо `Frontend / TypeScript`; свободное название компетенции остаётся отдельным полем.

Подписка одна на пару «шаблон — человек», а не на каждый вариант резюме. Один открытый запрос и минимальная недельная частота проверяются на человека для всех компаний и резюме. Перепривязка остановленной подписки не включает её: возобновить может только кандидат. Отказ от всех предложений, блокировка компании и прежние сроки не обходятся новым резюме.

При создании подписки и каждого предложения сервер сохраняет `resumeId`, `resumeRevision`, `resumeContext` и `resumeProvenance=captured`. Контекст содержит название, направление, подтверждённую категорию и навыки, профессиональный псевдоним, исходные ID и ревизию. В нём нет контактных полей, ответов экзамена или ключей оценивания. Предложение получает собственный неизменяемый контекст; триггер PostgreSQL запрещает замену его происхождения и условий задания.

Изменение основного резюме и обычная правка названия/ревизии не заменяют источник старого предложения. Скрытие, удаление, смена направления, снятие подтверждения или согласия на подбор прекращают доступ компании и останавливают связанную подписку. Ответ и результат остаются в истории владельца. Новые действия дополнительно проверяют текущее право на это резюме; сохранённый снимок сам по себе не предоставляет доступ.

Оценку компании выставляет человек по сохранённой рубрике. Результат `company_task` имеет `qualificationEffect=none`; общий грейд Signal не пересчитывается. Кандидат отдельно разрешает показывать результат. Другой работодатель получает только явно опубликованные результаты именно выбранного доступного резюме, без исходного ответа и личности оценщика.

## Старые записи

Миграция `0009_microtask_resume` не выводит прошлое происхождение из нынешнего основного резюме. Старые шаблоны получают `specialization=null`, старые подписки и предложения — `resumeProvenance=legacy_unbound`, пустые ID/ревизию/контекст. Интерфейс прямо сообщает об отсутствии сохранённого резюме.

Владелец может читать старый ответ и результат. Прежний адресованный компании ответ доступен ей только при известных записанных разрешениях и действующих настройках доступа; происхождение резюме при этом не заявляется. Новый ответ, новое предложение и публикация без доказуемого выбранного резюме запрещены. Для продолжения нужно явно выбрать подходящее резюме и направление шаблона; прежний ответ не переносится и не переоценивается автоматически.

## API и интерфейс

* `POST/PUT /api/employer/microtasks[/:id]`: обязательное закрытое поле `specialization`.
* `GET /api/employer/microtasks/eligible/candidates?templateId=…`: строки `id` человека, `resumeId`, `resumeRevision`, `resumeTitle`, `alias`, `specialization`, `verifiedGrade`. Неизвестный/чужой шаблон не даёт доступ; старый шаблон без направления возвращает пустой набор.
* `POST /api/employer/microtasks/:id/subscriptions`: строгий объект `{candidateId,resumeId}`. Активная подписка на другое резюме даёт конфликт; остановленную можно перепривязать без включения.
* Списки предложений и подписок возвращают сохранённый контекст и свежие `resumeAvailable`, `resumeLimitation`. Ответ компании при отзыве скрывает контекст, ответ и результат. Ответ владельцу сохраняет историю.
* `GET /api/employer/micro-evidence/:candidateId?resumeId=…`: `resumeId` обязателен. Старые несвязанные результаты не приписываются текущему резюме.

В форме компании варианты выбора представляют резюме, а не только псевдоним человека. Для каждого шаблона загружается собственный допустимый список. Кандидат видит название, направление, категорию и исходную ревизию у предложения; недоступные действия отключены с объяснением. Форма вакансии использует общий справочник ролей и навыков с собственными значениями, сохраняя фактические серверные ограничения: максимум 20 навыков по 60 символов. Новый город для вакансии не выдуман: такого поля в контракте нет.

## Согласованность и проверки

Мутирующие действия практики и планировщик после блокировки компании берут advisory-lock владельца резюме `(3306,userId)`, затем блокировку профиля. Операции резюме используют тот же advisory-lock до изменений. Отзыв не берёт блокировку компании внутри resume hooks, чтобы не создавать обратный порядок. Вставка подписки либо отправка нового ответа не может вклиниться между отзывом и изменением приватности.

Актуальный изолированный контроль: `outputs/verification/release-0.6.0/microtask-resume-http-a8d338df.json`, **16 групп PASS**, source API `4363`, PID `34296`, БД `signal_resume_v060_check`. Проверены вторичное резюме, категории/пулы/чужой владелец, параллельный повтор, неизменность истории, ручная оценка, точная публикация результата, пяти-резюмный недельный лимит, candidate-only возобновление, SQL constraints/trigger, четыре причины отзыва, блокировка компании, честное старое происхождение и две реальные privacy-first гонки. Тестовые аккаунты удалены по точной собственности; чужие записи не удалялись.

Фикстуры контроля используют явно синтетические известные квалификационные поля. Они не доказывают сдачу реального экзамена человеком. Две отдельные пары для проверки интерфейса созданы штатным контролируемым `provision-reviewers.ts`: **0 попыток, 0 выданных категорий**, секреты только во внешнем private-файле. Эти пары сохраняются до завершения проверки интерфейса.

Модульные проверки: 8 новых бизнес-проверок и 3 прежних проверок правил возможностей — **11/11 PASS**. Узкие тесты нового/исторического stage guards проверяют запрет другого контейнера/БД, старого набора миграций, заменённого OID/start, выдуманного backfill и изменения истории. Четыре реальные запросa хэширования нового guard выполнены только на отдельной контрольной БД без вывода строк.

Прежние неуспешные прогоны и предыдущий PASS14 сохранены под отдельными именами. Функциональный контроль source-tsx не является приёмкой обычного release-бандла, полного load, браузерного интерфейса или чистого архива 0.6.0. Эти этапы проверяются отдельно.

## План обновления существующего stage

Подготовлен `scripts/upgrade-owned-stage-v060.cjs`. По умолчанию `--check-only` не обращается к Docker/SQL. Выполнять stage-обновление можно только после отдельного разрешения root и освобождения API от записей; helper не управляет процессами и не предполагает, что прежний PID всё ещё актуален.

1. Root проверяет фактический PID, command line и старт своего stage API и сохраняет прежние runtime receipts. Пользовательские записи не очищаются.
2. `node scripts/upgrade-owned-stage-v060.cjs --capture-owned-stage-identity` сохраняет private ownership manifest: точный контейнер `signal-qa-cycle-01-db-1`, единственный loopback `55435`, БД `signal_resume_stage`, OID и старт контейнера. Требуется существующий полный набор до `0008`, без частично применённой `0009`.
3. Root освобождает окно записи. Только после разрешения: `$env:SIGNAL_STAGE_0009_RELEASE='1'`; `node scripts/upgrade-owned-stage-v060.cjs --upgrade-owned-stage`.
4. Helper делает бинарный `pg_dump` PGDMP во внешнем private-каталоге из того же экспортированного snapshot, что и полные хэши всех public-таблиц. Выполняется только штатная миграция, без seed/reset. После неё сверяются все старые поля/строки/дубликаты/удалённая история; исключены лишь девять новых полей `0009`. Старый `pool_content_digest` включён в сравнение и дополнительно проверяется для всех живых и удалённых резюме. Старые предложения обязаны остаться честно `legacy_unbound`, старые направления — `null`.
5. Публичный результат: `outputs/verification/release-0.6.0/stage-upgrade-0009.json`; в нём нет строк, ответов, контактов, credentials или путей private backup. Root отдельно запускает новый проверенный API и делает его функциональную приёмку.

По отдельному разрешению root обновление существующего stage **выполнено PASS**. `stage-upgrade-0009.json` подтверждает неизменные полные бизнес-коммитменты всех public-таблиц, binary PGDMP backup из того же snapshot и все305 фактических digest резюме (282 живых,23 удалённых). Эти количества относятся к моменту проверки, а не задают ожидания для будущих запусков. Seed/reset не выполнялись; старые предложения остались `legacy_unbound`.

Узкий `scripts/restart-owned-stage-v060.ps1` подготовлен отдельно и не запускает миграцию/seed/reset. До остановки процесса он требует source version0.6, точный SHA успешного `stage-upgrade-0009.json`, сохранение бизнеса, private PGDMP backup из того же snapshot, валидные digest всех live/deleted резюме, текущие migration source SHA, тот же контейнер/loopback/OID и фактические PID/start/private runner SHA. `ExpectedStartedAt` берётся из `Win32_Process.CreationDate`; одна и та же точность этого источника применяется до и после. `-CheckOnly` не читает stage и не управляет процессами.
