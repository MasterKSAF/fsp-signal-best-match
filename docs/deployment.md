# Развёртывание Signal 0.7.0

Для текущих исходников 0.7.0 актуальный вход — [техническое описание](technical-description-current-20261008.md) и [приёмка A01–A11](full-audit-a01-a11-20261008/report.md). При обновлении существующей установки сначала применить миграции 0010–0014, затем включить `SIGNAL_WORKSPACE_ENABLED=true` и `SIGNAL_SKILL_MODULES_ENABLED=true`. Миграция `0014_registration_challenge_snapshot.sql` связывает новую регистрацию с конкретной заявкой; старые неподтверждённые непривязанные коды требуют новой заявки. Подтверждённые аккаунты, сессии и доказательства не меняются. Новая установка выполняет все миграции до запуска API. Копировать новые исходники поверх немигрированной работающей БД недостаточно.

Описанные далее измерения 0.6.0 и [чистый запуск 0.5](source-release-0.5.0.md) остаются историческими результатами своих версий. Новая приёмка A10 отдельно фиксирует собственную БД, clean source build и ограниченную нагрузку актуального bundle; её нельзя смешивать с прежним тестом 5000 человек. Чистый Docker Compose запуск, конкурсный архив и внешнее развёртывание принимаются отдельно.

## Локальная установка

Целевая среда — Node.js 24 и pnpm 11.25.0. `package.json` закрепляет packageManager; установка выполняется `--frozen-lockfile`. Dockerfile использует закреплённый digest Node 24 и сам активирует pnpm 11.25.0. Compose закрепляет PostgreSQL 17 и Mailpit digest.

На **новой локальной копии**, при свободных стандартных портах:

```powershell
node scripts/setup-env.mjs
pnpm install --frozen-lockfile
docker compose up -d db mail
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Dev UI — 4310, API — 4312, PostgreSQL — 55433, Mailpit — 8026. Почта локальной регистрации поступает в Mailpit. `.env` и private manifests не входят в публичную поставку; значения setup-env предназначены для локальной настройки.

Полный контейнерный вариант:

```powershell
node scripts/setup-env.mjs
docker compose --profile full up -d --build
```

Веб/API — `http://localhost:4310`; готовность — `/api/healthz`. Контейнер сначала применяет миграции, затем при `DEMO_MODE=true` добавляет обзорный seed. После ошибки миграции приложение не начинает обслуживать запросы. Повторный seed сохраняет изменения существующих обзорных примеров и не открывает согласия ordinary/reviewer-аккаунтов.

Для второго стенда нужны отдельные имя проекта, БД, volume и порты. [Рецепт проверяющего](reviewer-access.md) использует 4334/55441/8034, создаёт private доступы вне проекта и не останавливает рабочий 4313/4314.

## Демонстрационные и обычные данные

Общий Demo показывает готовые синтетические профили. Reviewer-пара получает пустой закрытый документ и настоящий серверный экзамен: опрос, явное подтверждение уровня, сохранение ответов, оценку и ограничения повторов. `demoMode=true` здесь обозначает синтетический пул, не право обхода квалификации.

Пять резюме принадлежат одному аккаунту: они не создают пять людей, попыток или новых дат подтверждения. Практика фиксирует отдельное резюме и `purpose=company_task`; её оценка не присваивает грейд Signal. После скрытия, удаления, смены направления, отзыва разрешения или исправления квалификации новые действия проверяют актуальные права. Исторический снимок не обходит запрет.

## Внешняя конфигурация

[Письменные B7/B10 ФСП](official-written-qa-20261007.md) разрешают зарубежные облачные LLM и не устанавливают явных пределов Docker, весов модели или RAM; ресурсы должны быть обоснованы. Signal не требует внешней LLM. Прежние аппаратные ориентиры и собственные нагрузочные пороги не являются официальными ограничениями трека; фактические показатели ниже сохраняют свою область измерения. B3 допускает видео и рекомендует доступность стенда весь период экспертизы, но конкретный срок/адрес и исключение согласуются отдельно. Эти ответы не доказывают внешнюю доставку почты или подключение реестра и не разрешают новую передачу персональных данных.

Штатный `compose.yaml` — локальный демонстрационный профиль: он явно задаёт `DEMO_MODE=true`, `MAILPIT_URL` и loopback `PUBLIC_URL`. Одного изменения `.env` недостаточно для production. Внешней среде нужен отдельный override с `DEMO_MODE=false`, фактическим HTTPS PUBLIC_URL, `MAIL_TRANSPORT=smtp`, параметрами SMTP и собственными секретами БД/верификации. Порты БД и Mailpit наружу не публикуют.

SMTP-адаптер реализован через Nodemailer; локальная доставка проверялась отдельно. Это не подтверждение доставки через произвольного внешнего провайдера. Недоступная почта не заменяет верификацию готовым кодом. Секреты задаются закрытой средой, не передаются фронтенду и не включаются в архив.

Настоящая ФСП-интеграция требует предоставленного API и правил идентификации/согласия. Локальный провайдер содержит помеченные синтетические записи. Права модератора выдаёт административный инструмент; публичная регистрация их не даёт. Внешнее размещение, домен, HTTPS, реальная почта и публичные ссылки пока не заявляются выполненными.

## Обновление

Перед обновлением сохранить **свой** `pg_dump -Fc` и идентификатор работающего образа/исходников. Dump хранится вне конкурсного архива. Миграции идут по Drizzle journal; удаление таблиц не является откатом.

| Миграции | Смысл |
| --- | --- |
| 0004–0005 | Несколько резюме, сохранение прежних сведений/попыток, доверие и антиспам |
| 0006 | Неизменяемое назначение квалификационной попытки; прежние подтверждения автоматически не отзываются |
| 0007 | Reviewer-пары и scope сессии |
| 0008 | Полная серверная подпись резюме для свежих ключей пула |
| 0009 | Резюме/ревизия/контекст практики; старые записи `legacy_unbound`, без выдуманной привязки к текущему основному документу |
| 0010 | Независимые попытки навыков, свидетельства, история выдач, ограничения аккаунта и сертификаты категорий |
| 0011 | События просмотра/выдачи документов и условия работы конкретного резюме |
| 0012 | Локация и отдельные уровни навыков опубликованных вакансий |
| 0013 | Явные минимальные уровни навыков потребности работодателя |

Миграции сначала проверяют на восстановленной отдельной БД. Рабочее обновление требует контроля имени БД/процесса, backup и сверки бизнес-данных до/после. [Фактическое обновление именованного стенда 0009](../outputs/verification/release-0.6.0/stage-upgrade-0009.json) сохранило бизнес-данные и 305 digest: 282 live/23 tombstone; 271 пользователь, включая ordinary/reviewer/overview. Backup сделан из того же снимка. [Перечитывание после перезапуска](../outputs/verification/release-0.6.0/stage-post-restart-readonly.json) подтверждает сохранённое состояние, не нагрузку. Это не разрешение запускать helper против произвольной рабочей БД.

`docker compose down` сохраняет volume. `down --volumes` допустим только для созданного вами одноразового проекта после проверки его имени. HTTP-фикстуры убирают по точным ID своего запуска, не через reset общего seed.

## Восстановление

Восстановить dump в **отдельную пустую именованную БД**, применить соответствующую схему и сравнить число/хеши бизнес-записей, историю попыток, контактов и согласий. Проверить вход, резюме/доказательства/PDF и права до переключения трафика. Прежний restore 28 таблиц не доказывает восстановление новой многорезюмной схемы; версия и состав проверенного backup фиксируются своим протоколом.

Нельзя возвращать старый несовместимый образ поверх новой схемы. При проблеме остановить новые записи и использовать проверенный совместимый код либо отдельную восстановленную БД с оценкой изменений после снимка. Резервная копия не является публичным датасетом.

## Перед передачей

Последовательность: неизменный source → сборка/функциональная приёмка/нагрузка → документы с фактическими границами → source ZIP с manifest/SHA → отдельные privacy/чистый запуск именно ZIP → медиакомплект с визуальным просмотром → внешний комплект. Истинные статусы и точные SHA находятся в отдельных companion-протоколах и итоговом отчёте; отсутствие протокола не заменяется обещанием PASS. После source seal документы не пересобирают ZIP ради добавления поздних отчётов. ZIP 0.5 не перезаписывается. Наличие локального ZIP не означает отправку заявки.
