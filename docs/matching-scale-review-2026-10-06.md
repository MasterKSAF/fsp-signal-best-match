# Проверка масштаба подбора и исправление группировки

6 октября 2026 года. Исходная нагрузка на 5000 человек и 32 сессии провалилась; её отчёт `outputs/verification/multi-resume/load-baseline-one-resume.json` сохранён. Проверка ниже не заменяет повторную нагрузку.

## Конкретное исправление

В `rankMatches` на каждом добавлении перестраивались массивы двух группировок: `tiers.set(score, [...old, entry])` и `groups.set(key, [...old, entry])`. Для одного массива из 5000 элементов копируются 12 497 500 ранее добавленных ссылок; две группировки выполняют квадратичную работу. Теперь существующая локальная группа получает `push`, новая — массив с одним элементом. Политика допуска, формула, очереди, comparator, копирование входных объектов и результат не менялись.

Точная исходная версия сохранена до правки в `outputs/verification/history/multi-resume-before-rank-append/artifacts/api-server/src/lib/`. SHA-256 исходного matcher: `5132063b3585b3e3c7a3cc98644287288058994c1e9b6b12a29ae016ab9bde44`; после правки: `8d9564d2024c3ecd3d75f21eecf3dcd92fba986388b104a09a9ef40a745cccfe`.

`tests/matching-bucket-append.test.ts`: **3 PASS**. На 5000 кандидатах одной группы и 5000 кандидатах смешанных грейдов, версий, рубрик, неизвестного качества и соответствия потребности проверены полные evaluations, позиции, размер пула, отсутствие изменения входа, обратная/переставленная последовательность и prepared comparator. Они полностью совпали с сохранённым исходным кодом.

Существующие matching/admission/loader/catalog тесты: **49 PASS**. API typecheck: **PASS**. Логи: `outputs/verification/multi-resume/matching-bucket-append-unit.log`, `matching-bucket-append-goldens.log`.

Диагностическое время одного запуска rankMatches для одной группы: 208,81 → 37,01 мс; при обратном входе 202,91 → 22 мс. Смешанные группы: 122,90 → 144,85 мс и 102,32 → 58,32 мс. Это не отдельный калиброванный benchmark и не гарантированное ускорение всего API. Heap после теста включает fixtures и оба результата, не является измерением пика приложения.

## Что ещё обнаружено

- Поиск всё ещё повторно читает данные ранжирования целого допущенного пула на каждый запрос и при объяснении одного результата. Загружается проекция метаданных рубрики, а не весь private протокол. Исторический отдельный SQL-эксперимент на 1000 generated rows передавал 2 176 149 байт такой проекции; это не время нынешнего serving route. При большом числе запросов нужны измерение этапов SQL/JSON decode/evaluation и контроль параллелизма.
- `withResumeSkillEvidence` сейчас читает полный private протокол только выбранной страницы из 24 человек, одного объяснения или двух сравниваемых резюме. Его нельзя ошибочно называть полной загрузкой всех доказательств каталога. Он всё ещё может быть дорог при большой истории попыток одного человека; это отдельно от нынешней фикстуры с одной попыткой.
- Чтение пула выбирает public `avatarDataUrl` каждого резюме. С текущими pseudonymous фикстурами это не причина сбоя, но реальные фотографии до 2 MiB нельзя переносить целиком до пагинации; нужен флаг наличия фотографии для фильтра и чтение изображений выбранной страницы.
- `/matches` отдаёт весь допущенный пул; такое поведение было и в сохранённом 0.4. Ограничение ответа или пагинация — отдельный контракт, который нельзя вводить как незаметное изменение этой правки.
- Merge выбирает лучший head линейным обходом всех очередей на каждом выходе: O(N × G). Heap по тому же FSP/alias/ID comparator уместен только после измерения реального числа G; в этой правке merge не менялся.
- Override резюме использует `entries.find` только для явно выбранных людей. Ограничение API до 100 ID сдерживает этот путь; Map по resume ID может убрать поиск без изменения решения, но это не основной дефект текущей нагрузки.

Тот же квадратичный matcher присутствовал в сохранённом 0.4: прежняя успешная нагрузка на 1000 профилей не доказывала масштаб 5000 × 5 резюме. Материализованная квалификация не должна заменяться самозаявленными навыками. Любая последующая оптимизация обязана сохранить отзыв, текущие согласия, видимость, Demo/обычный пул, привязку identity и правило одной позиции на человека. Кеширование всего ответа без актуальной проверки этих границ недопустимо. Рабочая база и runtime этим изменением не затрагивались.
