# Общие данные кандидата: защита сохранения в разных резюме — 0.6.1

## Исправление P2

`PUT /api/me/candidate-profile` теперь требует две версии формы: `revision` выбранного CV и `identityRevision` общих имени, псевдонима, телефона и контактной почты. Старая форма B после изменения общих данных через A получает409 **до всех записей**, даже если сама ревизия B не изменилась. Общие поля остаются общими для аккаунта; специализация, содержание, согласия и квалификация сохраняют прежнюю принадлежность резюме.

Обе проверки выполняются внутри существующей транзакции после `pg_advisory_xact_lock(userId)` и `pg_advisory_xact_lock(3306,userId)`. До проверки PUT не создаёт первоначальное резюме/профиль. Callback изменения CV, пользователя, общей строки профиля, отзыва практики и пересчёта запускается только при совпадении обеих версий. Ошибка/откат транзакции сохраняет стандартную атомарность PostgreSQL.

## Контракт

- Owner GET/успешный PUT возвращает обязательные `revision` и `identityRevision`.
- Input также требует оба поля. `revision`: целое1…2147483647; `identityRevision`: ровно64 строчных hexadecimal-символа. Missing/malformed:400.
- PUT дополнительно требует явный `resumeId` в body: целое1…2147483647. Только queryID/отсутствующийID не выбирает основной CV для записи. GET безID по-прежнему читает основной CV и возвращает его `resumeId`; смена primary не может перенаправить старую форму на другой документ.
- Устаревший CV:409, `code: RESUME_REVISION_CONFLICT`.
- Устаревшие общие данные:409, `code: CANDIDATE_IDENTITY_REVISION_CONFLICT`, `error: Общие данные профиля изменились в другой вкладке. Обновите данные перед сохранением.`
- UI должен сохранить видимый черновик, предложить загрузить актуальную форму и потребовать осознанного повторного применения правок. Автоматический replay устаревшего тела недопустим.

`identityRevision` — SHA256 детерминированного JSON-массива: версия `signal-candidate-identity-v1`, userId и четыре фактических общих значения. Nullable контакты явно представлены `null`. Значения не приводятся к одному регистру, не обрезаются и не объединяются Unicode-нормализацией. Токен не является паролем или авторизацией; доступ по-прежнему проверяется по сессии/роли/владельцу.

Имя и общие поля читаются одним live SQL JOIN `signal_users`/`signal_candidate_profiles`; ответ не использует ранее прочитанное имя сессии. Токен одинаков у всех CV одного текущего общего снимка и не зависит от их грейдов, дат экзамена, фотографии, ФСП или updatedAt. Это версия содержимого: сознательный возврат всех четырёх значений к прежним возвращает прежний токен; отдельного исторического счётчика действий нет. Проверка ревизии самого CV сохраняется независимо.

Исходный `lib/api-spec/openapi.yaml` обновлён, выполнен штатный `pnpm codegen`; generated клиент и Zod-схемы не исправлялись вручную. Миграция не нужна. Экзамены, исторические доказательства, пороги, даты и квалификационные правила не изменялись.
