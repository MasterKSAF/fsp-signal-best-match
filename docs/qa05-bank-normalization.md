# QA-05: Unicode-навыки в каталоге кандидатов

Причина дефекта: matcher и отображение приводят навыки через NFKC, а прежний SQL-фильтр делал только lower/пробелы. Поэтому сохранённый через обычный профиль `Ｐｙｔｈｏｎ` отображался как Python, но терялся по фильтру Python.

Исправлен reader, а не пользовательские данные: SQL сначала выполняет `normalize(item, NFKC)`, затем сворачивает явный набор пробельных символов ECMAScript, обрезает пробелы и приводит регистр. Контролируемые aliases берутся из того же каталога. Применение остаётся внутри SQL перед COUNT/LIMIT; чтение всего каталога в JavaScript и миграция старых значений не нужны. Контакты и остальные приватные поля по-прежнему не выбираются.

PostgreSQL поддерживает NFKC в UTF8; lower использует локаль базы ([официальная документация PostgreSQL](https://www.postgresql.org/docs/17/functions-string.html)). Точное совпадение JS/SQL измеряется на перечисленных ASCII/Cyrillic/Unicode-эквивалентных и неизвестных токенах, а не на всех символах Unicode.

Осмысленные проверки: ordinary PUT с сохранением raw stack; отображение и фильтры известных aliases; исторический verified-массив без backfill; неизвестный навык без угадывания пунктуации; ввод, похожий на SQL; фильтры consent/private/pool/role; COUNT и три страницы для 27 Unicode-записей; сравнение SQL и JavaScript на независимых примерах. Указанный кандидатский stack не превращается в подтверждённый обязательный навык для подбора.

Функциональный сценарий `scripts/qa-cycle-01-bank.mts` разрешает только изолированный HTTP 4321 и PostgreSQL 55435. Он проверяет SHA исходных входов собранного контейнера, создаёт собственные синтетические записи, удаляет только захваченные ID после проверки email-префикса и сохраняет историю прогона. Рабочие порты 4310/55433 запрещены самим скриптом.

Протокол `outputs/verification/qa-cycle-01-bank.json` появляется после фактического HTTP/SQL-прогона; модульные проверки не выдают себя за собранное приложение. До этого `verified` для HTTP не заявляется.
