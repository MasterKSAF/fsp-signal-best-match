# Проверка эквивалентности экзамена Signal — 07.10.2026

## Исходный факт и 18 классификаций

Независимый аудит обнаружил 18 различающихся решений среди 234 пар A/B и 468 синтетических работ. Поштучная проверка показывает: **все 18 принадлежат заранее заданному профилю `one-template-method-only`**. Его преобразование `form-gap` намеренно заменяет ответ B на критичный slot0 строкой `synthetic-wrong`, оставляя A полностью правильной. Это не 18 наблюдений реальных участников и не оценка человеческой стабильности повторного экзамена.

В Backend A проверяет replay сохранённого ответа, B — optimistic write по версии. Во Frontend A работает с типизированным discriminated union, B — с runtime boundary для unknown. Общий идентификатор компетенции не делает эти методы одинаковыми. Первичная причина — различный профиль знаний, вторичная — различное содержание в широкой компетенции. Для этих переходов не обнаружено ошибки ключа или рубрики; порог не является причиной: B не проходит обязательный критичный критерий при каждом проверенном пороге.

## Исправленная ошибка рубрики

Старая рубрика сравнивала ответ типа integer как текст: математически одинаковые `2`, `+002` и `0002` получали разные результаты. В **Backend v7 / Frontend v3** добавлен сохранённый discriminator `answerComparison: canonical_integer_v1`. Он разрешает десятичное целое с необязательным знаком и ведущими нулями, сравнивает точные значения через BigInt, допускает только внешние пробелы. Условие новых заданий явно описывает разрешённую запись.

Не принимаются дробная запись `2.0`, экспонента `2e0`, единицы, разделители, внутренние пробелы, NaN/Infinity, Unicode-двойники цифр/минуса и неверное значение. Структурированные ответы не получили ослабления: порядок и число компонентов остаются значимыми.

Before/after: 36 одинаковых по числовому содержанию форм A/B × 14 представлений = **504 проверки** (180 разрешённых и 324 неверных/недопустимых). Старые версии отвергли 108 разрешённых представлений; новые не отвергли ни одного из этих 180 и не приняли ни одного из 324 отрицательных контролей. Это ограниченный форматный контроль, а не калибровка рыночного грейда. Отдельные unit controls проверяют точность за пределами Number.safeInteger, отрицательные числа и отрицательный ноль.

## Третья семантическая форма

Активный реестр содержит 108 шаблонов: три формы на каждую из шести компетенций двух программ и трёх уровней. Формы C меняют структуру задачи, а не только числа:

| Компетенция | Backend C | Frontend C |
|---|---|---|
| Контракт / типы | срок разрешения, граница истечения и fencing token | ноль и отсутствие, discriminant, конечное число |
| Данные / состояние | CASE, DISTINCT/NULL, tenant, условие JOIN в ON | частичное обновление, удаление ключа, stale action |
| Диагностика | lock wait, deadlock, inflight/retention | forced layout после чередования DOM read/write |
| Повторы / доступность | rollback не сохраняет dedup-отметку | клавиатурные вкладки и исчезнувшая цель фокуса |
| Архитектура | откат кода при уже записанном новом формате | offline/pending отдельно от server success |
| Изменённое условие / async | отрицательный кэш, TTL и revision | epoch, ошибка без записи, unmount |

Для 18 новых форм (2 программы × 3 уровня × 3 seed) независимо исполнен **показанный в условии** Python/TypeScript/SQL: 72 trace/SQL критерия совпали с ключами. Python и SQLite выполняют локальные авторские fixtures; TypeScript исполняется в локальном VM. Это не endpoint выполнения кандидатского кода. Выборы диагностики и архитектуры (slots2/4) не представлены как runtime-проверенные. Новые unit seeds отдельно проверяют все уровни.

Эксперимент разделяет стратегии:

1. Точное копирование готового вектора A в C не подтвердило грейд в 18 выбранных формах. Это факт о выбранном наборе, не универсальное обещание устойчивости.
2. Прежняя ограниченная модель изученного A-метода консервативно не понимает C: 18 `not_evaluated`. Они **не входят в число неуспешных переносов** и не доказывают устойчивость к заученному методу.
3. Исполнение полного видимого нового контракта проверяет семантику ключа. Оно не моделирует обучение человека/LLM и не является результатом античита. Освоенный метод может законно решать незнакомую форму.

## Независимый замороженный структурный контроль

Отдельный автор, не читавший scorer, oracle, индивидуальные 18 результатов или генератор, подготовил 24 ручных кейса и явные стратегии. Freeze SHA набора `f79d00fe…` сделан до просмотра текущего оценивания; 12 diagnostic отделены от 12 holdout. Информация о правилах программы и агрегатах была видна в публичном managed-документе, поэтому независимость ограничена именно этой границей.

Финальный runner и протокол заморожены до первого раскрытия holdout. В отчёте воспроизведены **заранее заданные ручные предсказания** literal copy и limited method. Средние диагностические component scores: copy23,61 / method22,22; holdout copy22,22 / method19,44. Это не измеренное поведение обучаемого решателя. Полное семантическое эталонное решение не включено как эмпирический 100% результат, его empirical result равен null. Новизна заявлена относительно указанного учебного примера, не всего возможного банка.

После фактического прогона восстановлен исходный per-file стиль LF/CRLF без изменения токенов, условий или labels. `source-line-ending-association-final.json` связывает реальные SHA исполнения с текущими файлами по точному canonical-LF равенству. Исторические timestamps/hashes не переписаны; holdout не переиспользован для настройки. Затем изменён только репортёр: уникальные имена, запрет перезаписи существующего отчёта до вычислений и честный firstFinalReplay=false для повторов. Второй actual replay даёт те же historical/integer/semantic rows и manual predictions; он не объявлен новым untouched holdout. `reporting-guard-check.json` фиксирует сохранение исходных байтов и отказ повторной записи.

## Совместимость и сохранение истории

Обычный сервер выдаёт v7/v3. Server/test-only historical assembler воспроизводит Backend v5/v6 и Frontend v1/v2; клиент не может выбирать версию, форму или rubric policy. Сохранённые v4/v5/v6/v1/v2 попытки оцениваются по их исходным blueprint и правилам. Новый integer marker запрещён на старых версиях и обязателен только на integer-слоте новых версий. Нет migration/regrading старых результатов или автоматического понижения грейда.

Матрица доказательств v2 добавляет только identity-правила новых версий. Она сохраняет исходные версию, дату, критерий и уровень. Весь грейд не переносится между программами, а историческое подтверждение не переименовывается в экзамен v7/v3. Явная коррекция остаётся существующим отдельным механизмом.
