# Исходники и чистый запуск Signal 0.5.0

Эта инструкция описывает подготовленный новый протокол. Сам файл не подтверждает выполненную упаковку, чистый запуск, browser-приёмку или нагрузку. Фактический результат появится отдельными отчётами в `outputs/release-0.5.0`. Комплект и отчёты 0.4.1 сохраняются как история.

До финальной заморозки разрешены только синтаксические проверки, проверки выбора файлов и unit-проверки guards. Не запускать новую сборку рядом с полной нагрузкой; не занимать рабочий веб 4310, stage API 4313/UI 4314 и отдельный нагрузочный 4315.

## Контракт заморозки

Владелец релиза создаёт `outputs/release-0.5.0/release-freeze.json` после функциональной, браузерной и обеих полных нагрузочных фаз. Это публичный протокол без аккаунтов, паролей, cookie, токенов, ответов экзамена и connection strings.

Обязательные поля:

- `schemaVersion: 1`, `applicationVersion: "0.5.0"`, `status: "frozen-for-source-seal"`, `frozenAt`.
- `sourceHashes`: словарь точных относительных путей и SHA256 текущих исходников. Включает `package.json`, `pnpm-lock.yaml`, `artifacts/api-server/build.mjs` и `artifacts/api-server/build-portability.mjs`, matcher, auth, pool-scope, assessment-purpose, `lib/db/src/schema/fsp-signal.ts`, `lib/db/src/schema/signal-resume.ts`, миграции 0006/0007 и `lib/db/migrations/0008_resume_pool_digest.sql`, а также `lib/api-spec/openapi.yaml`. Отсутствие schema, атомарного digest trigger/index migration или build helper блокирует seal.
- `acceptedRuntime`: `applicationVersion: "0.5.0"`, SHA256 реально принятого API bundle в `bundleSHA`, непустой `sourceHashes`. Все runtime-пути и SHA должны совпасть с общим `sourceHashes`; архив проверяет точную принятую сборку.
- `publicProofInputs`: не более 64 уникальных `{path, sha256}` для конкретных публичных JSON/MD/TXT/CSV новой приёмки. Можно выбрать точные вложенные отчёты; рекурсивного доступа к `outputs` нет. Private, screenshots/raw, clean extraction и post-seal отчёты запрещены.

Дата ZIP entries берётся из `frozenAt`, преобразованного в UTC, с двухсекундной точностью ZIP. При той же заморозке она воспроизводима; новая версия получает дату своей заморозки вместо общей фиксированной даты. Байты исходников не изменяются. Дополнительная timestamp-only защита чистого запуска проверяет содержимое независимо от даты извлечения.

Для воспроизводимости прежнего синтетического исследования включены ровно пять публичных файлов `outputs/research/confirmation-v1`: `protocol.json`, `freeze.json`, `protocol.sha256`, `results.json`, `results.md`. Их точные неизменные SHA находятся в `scripts/source_research_inputs_v050.py`. Это отдельное разрешение только на эти пути и байты, включая единственный hash companion `.sha256`; соседние файлы и другие research-каталоги запрещены. Контроль содержит 17 синтетических сценариев и 0 участников-людей; повторное включение в новый архив не становится новой валидацией на людях.

Две дополнительные frozen golden зависимости теста `matching-bucket-append.test.ts` добавлены отдельным versioned allowlist с точными SHA в `scripts/source_qa_inputs.py`. Старые 9 обязательных inputs, 2 необязательных history inputs и 2 исторических контрольных отчёта сохранены. Их прежние даты/SHA не становятся новой приёмкой. Новые golden TS — единственное дополнительное разрешение на TS внутри `outputs`.

## До заморозки: без архива

Из корня проекта:

```powershell
python -m unittest discover -s tests -p test_source_v050_policy.py
python scripts/package-source-v050.py --check-only
```

`--check-only` не записывает ZIP. Если freeze уже существует, он также проверяет его точные исходники и набор публичных доказательств. Изменение принятого кода после freeze блокирует упаковку.

## После явной заморозки

1. `python scripts/package-source-v050.py` создаёт только новый `outputs/release-0.5.0/fsp-signal-source-0.5.0.zip`. `SOURCE-MANIFEST.json` содержит все пути, SHA256 и размеры; `RELEASE-METADATA.json` связывает текущий matcher, программы, freeze и принятый runtime. Предыдущую попытку нового seal сохраняют в `outputs/release-0.5.0/history`; архив 0.4.1 не изменяют.
2. Выполнить `python scripts/audit-source-privacy-v050.py --expected-sha256 <SHA256 нового ZIP>`. Добавить `--private-manifest <абсолютный внешний JSON>` для каждого сохранённого локального reviewer/QA manifest. Проверяются CRC, manifest, paths, frozen inputs, secret patterns и совпадения с локальными private значениями. В отчёт попадают только количества и fingerprints, без значений. Этот аудит ограничен известными значениями и шаблонами, не является универсальным доказательством отсутствия секретов.
3. В PowerShell 7 выполнить `scripts/clean-source-launch-v050.ps1 -ExpectedSha256 <тот же SHA256> -FreezeReleased`. Нужен privacy PASS ровно этого ZIP. Повторно проверяются свободные порты **4330 / 55439 / 8033**; чужие процессы не останавливаются.

Новый запуск использует случайный Compose project `signal-clean-v050-<id>` и отдельную БД `signal_clean_v050_<id>`. Рабочую `.env` не копируют. Пароли БД и verification secret создаются случайно в окружении этого процесса и не входят в исходники/отчёты. Перед seed проверяют, что новая БД пуста.

## Версии инструментов

`clean-source-launch.json` записывает `runtimeVersions`: фактические host Node/pnpm/Python/PowerShell, отдельно `configuredPackageManager` из запечатанного `package.json`, целевой pnpm из запечатанного Dockerfile и фактически измеренные Node/pnpm нового контейнера. Скрипт не устанавливает и не меняет глобальный toolchain.

При подготовке 07.10.2026 host имел Node `v24.14.1`, pnpm `11.19.0`, Python `3.11.9` и PowerShell `7.6.2`. Это наблюдение подготовки, не заранее присвоенный результат будущему clean. `packageManager` и Dockerfile задают `pnpm@11.25.0`; host `11.19.0` не называется `11.25.0`. Успешный host `pnpm install --frozen-lockfile` и неизменный SHA lockfile подтверждают установку зафиксированного графа зависимостей этой host CLI. Они не доказывают равенство её версии Docker CLI. В контейнере целевой `11.25.0` проверяется по реальной команде `pnpm --version`; расхождение блокирует clean PASS. Docker Node также записывается из контейнера, а не копируется из host receipt.

## Что фактически проверяет чистый запуск

- Свежая установка зависимостей по lockfile и полный unit suite из распакованного источника; отдельные guard unit-проверки. Количество Node/Python tests и PowerShell guard-групп берётся из фактического вывода именно этого запуска, без закреплённого старого количества.
- Три offline контроля ранжирования: новые отчёты с SHA текущего matcher и сравнение содержательных результатов с неизменными frozen историческими сценариями. Никаких новых quality labels, улучшения метрик или утверждения о человеческой валидности грейда эта проверка не создаёт.
- No-cache Docker build, новые миграции и обзорный Demo seed; доступность реального сайта/программ. Перед сборкой clean tool проверяет SHA всех запечатанных файлов контекста, обновляет только `LastWriteTimeUtc` собственных извлечённых копий и повторяет SHA-проверку. Это устраняет воспроизведённое повторное использование Docker Desktop старых файлов с одинаковыми размером и фиксированной датой ZIP. Байты и сам ZIP не изменяются; `--no-cache` без проверки контекста не доказывает их свежесть.
- Обычная регистрация с email-подтверждением через собственный Mailpit HTTP transport, отсутствие выдачи кода в API, запрет входа до подтверждения и повторного использования кода. Это реальная локальная доставка в Mailpit; production SMTP данной clean-проверкой не заявляется. Подстановка Demo/reviewer/scope не повышает права.
- Обязательный purpose и явное подтверждение уровня Signal qualification; без заполненного опроса обычный кандидат и reviewer не проходят стартовый gate. Два новых reviewer-набора создаются controlled tool, проходят реальные серверные попытки с независимыми ответами/возобновлением/завершением. Эталоны не читаются, желаемый грейд не присваивается, cooldown не обходится. Подробный самостоятельный маршрут — `docs/reviewer-access.md`.
- Пять совместимых копий резюме, лимит шестой копии, приватность новых копий, дедупликация каталога и стабильность полного matching-порядка, согласованность explanation. Это короткая содержательная регрессия и не подмена двух полных нагрузочных фаз.
- Реальный PDF собственного резюме: бинарная сигнатура/EOF, Content-Type, ненулевой размер и заголовок конкретного resumeId. Визуальную browser/PDF-приёмку эта HTTP-проверка не объявляет.
- Source/bundle attestation нового контейнера против manifest и всех исходников принятого runtime, включая build/generated/workspace файлы; точное совпадение SHA с принятой штатной сборкой обязательно. Build helper сохраняет worker assets и выбирает их расположение из самого ESM bundle; абсолютный путь машины сборки в него не записывается. Прочие отличия скомпилированных файлов не игнорируются и не нормализуются после сборки. Удаляется только новый Compose project и его volume. Свои обычные/reviewer записи удаляются точным guard; другие БД не запрашиваются и не сбрасываются.

Публичные результаты: `source-seal.json`, `source-privacy-audit.json`, `clean-source-launch.json`, `clean-http.json`, `clean-reviewer-http.json`, `clean-runtime.json` и `offline/*.json` в новом каталоге версии. Post-seal отчёты не входят в ZIP, который они проверяют. Guard сохраняет до/после идентичность существующих listeners и работающих Docker containers; это подтверждение идентичности runtime, а не доказательство всех возможных параллельных изменений строк чужой БД.

Самостоятельное прохождение человеком с reviewer доступами не выполняется автоматически. Для него выдаются новые private доступы вне исходников по `docs/reviewer-access.md`; сохранённые пароли не публикуются.
