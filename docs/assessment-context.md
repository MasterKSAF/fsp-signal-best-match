# Проверка навыков под требования роли

На 7 октября 2026 новые версии — `signal-backend-python-v7` / `signal-frontend-typescript-v3`. Историческое описание ниже относится к прежним формам; [актуальные изменения и проверки](assessment-equivalence-audit-2026-10-07.md) сохраняют прежние оценки и пороги.

Обновление 6 октября 2026: новые попытки используют управляемые `signal-backend-python-v6` и `signal-frontend-typescript-v2`; ниже сохранено историческое описание первоначальной реализации контекстов v4 и её проверок. У новых Senior четыре критичных критерия, включая архитектуру; прежние снимки не пересчитываются. Полная актуальная карта — [assessment-managed.md](assessment-managed.md). `/assessments/contexts?programId=frontend-typescript` предоставляет три Frontend-роли, Backend остаётся значением по умолчанию. Покрытие требований берётся из единого каталога: PostgreSQL не подтверждается общим SQL.

Состояние: 5 октября 2026 года. Версия контекстов: `backend-role-context-v1`. Банк и шкала оценки: `kalibr-backend-python-v4`.

## Что реализовано

Кандидат выбирает одну из трёх программ Backend / Python или полученное приглашение. В приглашении направление определяется по описанию роли и обязательным навыкам, а целевая категория берётся из потребности работодателя. Перед первой проверкой обычный аккаунт должен пройти первичный опрос в профиле. Пример аккаунта доступен без этого шага.

| Описание роли | Прикладная диагностика | Прикладная архитектура |
| --- | --- | --- |
| Разработчик API: API, контракты, HTTP, публикация событий | Запрос, блокировки или регрессия canary | Запись изменения и надёжная публикация события |
| Разработчик сервисов данных: SQL, обработка данных, поток событий | Запрос, миграция или регрессия данных | Доставка, конкурентная обработка или развитие контракта события |
| Разработчик надёжных сервисов: инциденты, нагрузка, восстановление | Очередь пула, трассировка или replay после failover | Восстановление операции нескольких сервисов и компенсация |

Внутри каждой строки задания усложняются от Junior к Middle и Senior. Изменяются реальные ситуации, варианты ответа и серверный критерий: это не только разные заголовки. На странице работодателя доступна карта «требование → семейство заданий → проверяемое действие» и целевая категория. Категория берётся из потребности, а не выдаётся за предсказание модели.

Автоматический выбор направления использует открытые правила: совпадение ключевой группы в названии/описании даёт 1 балл, в обязательных навыках — 2. Выбирается направление с максимальной суммой; при равенстве — порядок API, данные, надёжность. Без совпадений используется API как общее направление. Для других специализаций явно возвращается `supported: false`.

Проверка базовых API или событий не подтверждает владение конкретным фреймворком или брокером. Например, FastAPI, Kafka, Redis и неизвестные требования показываются как отдельно не проверенные. Это не мешает работодателю указать их в потребности.

## Как сохраняется сопоставимость

Каждая форма содержит шесть семейств в одинаковом порядке. Четыре общих задания — API-контракты, SQL, идемпотентность и изменение условий — используют один генератор независимо от роли. На одном скрытом seed эти задания точно совпадают между тремя профилями. Диагностика и архитектура выбираются под роль.

Для всех программ одинаковы:

- четыре задания с числовым/структурированным ответом и два с выбором;
- три критичных критерия, которые нужно выполнить полностью;
- равный вес каждого из шести семейств и прежняя частичная оценка компонентов;
- порог 67 для Junior, 83 для Middle и Senior;
- срок попытки 45 минут, повтор категории через 7 дней, повышение через 90 дней;
- политика сохранения ранее подтверждённой более высокой категории.

Это конструктивное обеспечение единой шкалы, **не доказательство равной психологической сложности** контекстов. Для такого вывода нужны независимые участники и экспертная разметка; человеческий пилот пока не проведён.

## Сохранение и доступ

При создании контекстной попытки в отдельную таблицу `signal_assessment_contexts` записывается неизменяемый снимок: версия, направление, целевая категория, название роли, проверяемые и непокрытые требования, карта покрытия. Изменение потребности позднее не меняет уже выданную форму и её объяснение.

Кандидат видит только свои попытки и собственные приглашения в статусах `sent`, `viewed`, `accepted`. Выбрать произвольный `needId` нельзя: при старте принимается только `invitationId`, проверяемый сервером. Контакты и внутреннее описание компании в снимок не входят. Работодатель читает карту только для потребности своей компании.

Снимки и публичные профили не содержат seed, веток генератора, правильных ответов или `oracles`. Правильный вариант присутствует среди вариантов выбора как часть задания, но никак не помечается.

Старые попытки v4 остаются доступными. Для них endpoint описания возвращает `snapshot: null`. Старый клиент может не передавать контекст и получить исходную общую форму v4. Новая форма интерфейса выбирает API по умолчанию. Добавление контекста не сбрасывает историю и не обходит ограничения повторов.

## Собственная автоматическая проверка

Команда: `node --import tsx --test tests/assessment-context.test.ts`.

Результат: **4 теста прошли**. Проверены **900 форм**: 3 направления × 3 категории × 100 воспроизводимых seed.

1. Три описания вакансий выбирают ожидаемые разные профили; неизвестные технологии остаются непроверенными.
2. Каждая форма проходит проверку целостности v4. Все четыре общих задания совпадают для одинакового seed. Архитектурные условия и правильные ответы различаются между тремя профилями. Диагностика надёжности отличается от профилей API/данных.
3. Полные правильные ответы дают 100; каждый из шести одиночных пропусков даёт одинаковую оценку и решение между профилями. Форматы, критичные флаги и временные ориентиры одинаковы.
4. Отсутствие контекста сохраняет старое поведение; сериализованные попытки v4 валидны; публичные описания и снимки не содержат служебных ключей или контактов компании.

Эти проверки подтверждают свойства алгоритма и структуры форм. Они не измеряют качество найма, рыночный грейд или точность работы с реальными кандидатами. Проверки HTTP-авторизации и нового пути регистрации выполняются отдельно в интеграционном прогоне.

## Точки расширения

Новые специализации требуют собственного банка и проверки сложности. Для текущего Backend можно добавить независимые задания той же рубрики после экспертного сравнения с общими заданиями. Реальный подбор направления по описанию вакансии можно расширять правилами или моделью, сохраняя объяснение выбора, список непокрытых требований, общий банк и неизменяемый снимок.

Контракт API приведён в [assessment-context-openapi.yaml](contracts/assessment-context-openapi.yaml). Пользовательские компоненты: `AssessmentContextSelector`, `AssessmentContextSummary`, `EmployerAssessmentContext`.
