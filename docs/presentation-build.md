# Сборка презентации

`scripts/build-pitch.mjs` импортирует официальный PPTX и редактирует его объекты. Использует исходные слайды 7, 8, 9, 10, 11, 13, 14, 18, Montserrat, логотипы, цвета и размеры 12192000 × 6858000 EMU. Готовая презентация содержит 8 слайдов. Текст остаётся редактируемым. Скриншоты приложения являются растровыми иллюстрациями с синтетическими данными.

Сборка презентации отделена от сборки приложения. Она требует установленного рабочего runtime Codex с `@oai/artifact-tool`, шрифтом Montserrat и Python с ReportLab/pypdf. Официальный шаблон и свежие скриншоты должны быть доступны по путям конфигурации. Docker приложения не зависит от этих инструментов.

## Обновление

1. Указать актуальные скриншоты, числа тестов и заметки в `docs/presentation-content.json`. Сверить их с текущими протоколами. Для 0.4.1 это matching v5 и transfer model v4. Все три снимка имеют точный исходный образ 55a5. При оптимизации только двух backend-путей допускается новый принятый runtime по отдельному протоколу ограниченной эквивалентности; происхождение старых снимков не переписывается. Флаг `draft` остаётся `true`, пока факты, снимки и приёмка не согласованы.
2. После согласования входных данных отключить `draft` и запустить из корня проекта:

```powershell
C:/Users/Misha/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/bin/node.exe scripts/build-pitch.mjs
```

3. Генератор создаст отдельную папку `outputs/internal/pitch-completion/<время-сборки>`. В ней находятся промежуточный PPTX, `validated/Signal-Pitch.pptx`, точные изображения сохранённых слайдов, визуальный PDF, протокол валидатора и происхождение материалов.
4. Просмотреть каждый `final-slide-N.png` и страницы PDF. Проверить актуальность UI, переносы, границы, цвета и соответствие шаблону. Автоматический валидатор не заменяет визуальный просмотр.
5. Скопировать только просмотренные, неизменённые PPTX/PDF в `outputs/submission`, сохранив прежний выпуск отдельно. В `outputs/verification/presentation-completion.json` записать фактические хеши, источник шаблона и результат просмотра всех восьми слайдов. Финальное согласование всего комплекта выполняется после новых протоколов видео, нагрузки и чистого запуска исходного ZIP; эти проверки не подменяются валидатором презентации. Не переиспользовать отчёт предыдущей версии.

Builder проверяет SHA каждого источника из конфигурации. Отличающийся runtime разрешён лишь по `signal-bounded-media-equivalence-v1`: frontend bytes совпадают, matching core и transfer model неизменны, изменены ровно четыре backend-пути: `assessment-ranking-evidence.ts`, `matching-pool-admission.ts`, `skill-catalog.ts` и `signal-employer-matching.ts`. Новая независимая приёмка 20 matching-групп и нагрузка должны действительно пройти на этом же образе/bundle. Все доказательства проверяются по SHA, backend bytes сверяются с текущими исходниками. Это ограниченная совместимость снимков, а не повтор всех старых проверок на новом образе.

Builder блокирует `--publish`: повторная генерация не является визуальной приёмкой. Скриншоты остаются растровыми иллюстрациями; текст, исходные фигуры, оформление и заметки PPTX — редактируемые объекты.

Для другой среды доступны `ARTIFACT_NODE_MODULES`, `ARTIFACT_PYTHON`, `PRESENTATIONS_SKILL_DIR`, `PITCH_TEMPLATE`. `PITCH_BUILD_ID` задаёт имя новой внутренней папки; финализатор не перезаписывает уже существующий итоговый файл.

PDF служит визуальной копией точного сохранённого PPTX. Он строится из рендеров слайдов без зависимости от шрифтов на компьютере зрителя. Для редактирования и копирования текста используется PPTX. Нативная проверка в Microsoft PowerPoint не подменяется рендером Artifact Tool.

## Питч

`docs/pitch-script.md` содержит речь по тем же восьми слайдам и ответы на вопросы. Три минуты являются планом. Фактический хронометраж подтверждается только реальной репетицией команды.
