# Браузерная приёмка Signal 0.5.0

Дата: 06.10.2026. Стенд: UI 4314 / API 4313, отдельная `signal_resume_stage`. Обычный рабочий стенд 4310 и нагрузочная БД не использованы. Ниже — фактически выполненные действия через интерфейс. Это техническая проверка агента, не пилот с независимыми людьми и не официальный балл конкурса.

## Независимые проверяющие

Использованы два контролируемых reviewer-набора с разными server-only scope и отдельными компаниями. Cookies разделены между `127.0.0.1` и `localhost`. Доступы сохранены только во внешнем private manifest; в исходники и публичный отчёт они не входят. Вход показывает «Самостоятельная проверка», обзорный Demo — отдельный режим.

1. Первый кандидат заполнил Backend/Python опрос и явно подтвердил Junior. Сервер выдал новую попытку 10418 с шестью задачами. Ответы решены по видимым условиям: скрытые эталоны не читались, грейд и баллы в БД не присваивались. Сохранение двух ответов и перезагрузка восстановили их с сервера. После остальных ответов реальное завершение дало 100/100 и подтверждённый Junior.
2. Второй кандидат заполнил свой опрос, явно выбрал Middle и получил иную попытку 10419. Один заведомо неполный ответ сохранён и восстановлен после повторного входа. Завершение с пятью пустыми ответами потребовало подтверждения в диалоге и дало 0/100 без квалификации. Первый результат не изменился.
3. Повторные входы вернули каждому собственную историю и ответы. Запрос чужой попытки из второго аккаунта не показал ни задачи, ни ответы, ни результат (HTTP 404). После уточнения текста отказ повторён на API 0.5.0: «Попытка недоступна. Она не найдена или принадлежит другому аккаунту», доступна ссылка на собственную историю.
4. Повтор Middle и повтор с совместимой копией резюме отклонены до 13.10.2026. Копия не снимает общий cooldown и не создаёт новую квалификацию.
5. У первого работодателя каталог содержит только опубликованный профиль первого кандидата; у второго — пустой каталог. Обзорный Demo и другой reviewer-набор не попадают в эти пулы.

## Пять резюме и редактирование

- Первый кандидат создал четыре копии, достигнув общего лимита пяти; кнопка копирования стала недоступна. Копии закрыты, публикация и согласия не включены автоматически.
- В последней копии выбраны Frontend/TypeScript и новый стек. Неприменимая Backend-квалификация не показана, дата квалификации отсутствует, новый опрос содержит 0/6 ответов. Обнаруженный stale-query дефект специализации исправлен отдельным ключом запроса.
- Копия удалена через диалог приложения. Осталось четыре резюме, исходный экзамен и Junior сохранены. При выборе другой копии старый `attempt` удаляется из URL; неизменный target экзамена не подменяется.
- Сохранение профиля, затем опроса, затем профиля проходит последовательно без ложного конфликта ревизий.
- В двух вкладках одного резюме оставлены разные несохранённые названия. Первая сохранила «Python · HTTP API»; вторая получила «Резюме изменилось в другой вкладке. Обновите данные перед сохранением». Её черновик остался в поле. После перезагрузки показано название первой вкладки: чужая правка не перезаписана.

## Приглашение и контакты

Первый работодатель создал собственный запрос Python/SQL, Junior, 100–150 тыс. ₽ в месяц до вычета, удалённо/гибрид. Подбор показал одного кандидата, соответствие 100 и отдельный результат экзамена 100/100. Приглашение адресовано конкретному резюме. Во второй компании список приглашений остался пустым.

Кандидат сначала прочитал компанию, условия и сообщение, затем явно принял приглашение с передачей контактов этой компании. После повторного входа работодатель увидел статус согласия и контакты. Кандидат отозвал дальнейший доступ; после нового входа работодатель видит «Кандидат отозвал доступ к контактам», сами контакты отсутствуют. Это проверка собственного синтетического набора, внешним людям сообщения не отправлялись.

## Каталог и парное сравнение

В ordinary-пуле использованы ранее созданные явно синтетические fixtures; это проверка интерфейса, не новые результаты независимых людей. Для собственной потребности компании 232 выбраны первые две карточки из семи разных людей. Диалог сравнения показывает одинаковый fit и позиции 1 и 2 из 7, поясняя, что порядок по псевдониму/ID не означает преимущество квалификации. Пул не подменён сравниваемой парой.

В каталоге одновременно выбраны Frontend/TypeScript, Junior и навыки `TypeScript, React`: результат 0. При тех же остальных фильтрах и только TypeScript: 7. Самозаявленный React не принят как подтверждённый навык. Нагрузочная/API-приёмка отдельно проверяет большой пул, дедупликацию и фильтры одного целого резюме.

Итоговое соответствие всех протоколов замороженному runtime фиксируется release manifest; ранние UI-сценарии выполнялись до последней оптимизации только чтения пула. Старые результаты 0.4.1 новым кодом не названы.

Скриншоты сохранены в новом каталоге `outputs/release-0.5.0/media`, прежние конкурсные материалы 0.4.1 не изменены. CUA фактически возвращает JPEG: собственные файлы переименованы в `.jpg` без изменения байтов; для видео допускается только отдельно проверенная перекодировка в PNG с точным равенством декодированных пикселей.

## Исправление повторного входа · 7 октября

После перехода ordinary работодателя к reviewer-кандидату клиент показывал 0 резюме, хотя авторизованный HTTP того же человека возвращал его 4 собственные записи. Глобальный `queryClient.clear()` отсоединял уже смонтированный auth observer; новый дочерний кабинет видел новый аккаунт, а root selector оставался в прежнем состоянии.

Вход и выход теперь отменяют старые запросы, удаляют только данные предыдущего пользователя и обновляют существующий auth query. Две содержательные регрессии с настоящим TanStack QueryObserver подтверждают доставку logout/new-session уже смонтированному observer и запрет позднему старому запросу вернуть чужие данные.

В браузере после загрузки исправленного клиента проверены без дальнейшей перезагрузки: reviewer-кандидат → выход → повторный вход кандидата → выход → его работодатель → выход → кандидат. Вернулись 4 резюме, основной Python/Junior, 7 подтверждённых навыков и собственное приглашение; профиль второй localhost-сессии сохраняется отдельно. Кадр `auth-role-switch-own-resumes.jpg` показывает восстановленный кабинет. Новый серверный экзамен не создавался, данные/права/кулдауны не сбрасывались.
