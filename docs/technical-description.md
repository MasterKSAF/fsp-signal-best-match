# Signal
## Техническое описание

Спецтрек ФСП, ЛЦТ 2026. Best Match. Срез исходников Signal 0.4.1: 6 октября 2026. Подбор `fsp-signal-match-v5`, политика `need-fit-traceability-comparable-queues-v2`; банки Backend v6 / Frontend v2.

**Фактическая приёмка 0.4.1.** Исторический checkpoint image55a5: независимые 60 групп HTTP/UI, включая QA-01/01b/03/04/05; обычная регистрация обеих ролей и видео 138 секунд / 21 сцена. Новый imagef5c067 после оптимизации чтения: 155 unit, typecheck, 6 изолированных HTTP-групп, независимые 20 групп и исходная нагрузка 1000 профилей / 32 сессии PASS. Три source-контроля воспроизвели прежние результаты; совместимость видео подтверждена отдельно. QA-02/02b остаются принятой узкой моделью `signal-source-mechanism-transfer-v4`; прежние неудачные нагрузки сохранены. Чистый запуск точного ZIP выполняется после seal с companion-протоколом.

**Нужные люди. Подходящая работа.** Signal связывает работодателя и кандидата через проверенные навыки, объяснимое соответствие задаче и приглашение с зарплатой. Контакты открываются конкретной компании по решению кандидата.

Центральный сценарий: потребность → категория → подбор → приглашение с условиями → решение кандидата → адресный контакт.

### Что входит в прототип

Две роли, регистрация, резюме/PDF, опрос, две программы Junior/Middle/Senior, каталог, подбор, приглашения, вакансии/отклики, регулярная практика и отдельный A/B. Три темы; Demo в форме входа.

# 1. Архитектура и доверенные границы

Signal использует модульный монолит: одна серверная бизнес-логика обслуживает веб для двух ролей, данные хранятся в PostgreSQL. Контейнер раздаёт собранный интерфейс и API с одного origin. Для разработки Vite проксирует /api к отдельному API-процессу.

| Слой | Ответственность |
| --- | --- |
| artifacts/fsp-signal | React, формы, кабинеты, проверки, каталог, объяснения, темы и помощник. Клиентское скрытие кнопки не считается контролем доступа. |
| artifacts/api-server | Express, Zod, авторизация, оценивание, единый допуск и score, согласия, PDF, письма, расписание практики и исследовательские маршруты. |
| lib/db | Drizzle и PostgreSQL 17: пользователи, профили, компании, попытки, потребности, приглашения, разрешения, публикации, задания и исследования. |
| lib/api-spec | OpenAPI 3.1; генерация Zod и React Query клиента. Спецификация доступна локально по /api/openapi.yaml. |
| Локальные компоненты | PostgreSQL и Mailpit в Compose. Шрифты и assets лежат в исходниках; Google Fonts и внешняя LLM для работы не требуются. |

### Состояния и сохранность

Миграции применяются последовательно, включая новые таблицы после исходных 0000 и 0001. Журнал Drizzle хранит применённые версии. Миграция разрешений добавляет технический ID и альтернативное основание отклика, сохраняя прежние строки приглашений. Рабочие аккаунты и историю не сбрасывают ради обновления приложения.

Выданные условия теста, рубрика, ключ и ответы принадлежат конкретной попытке. Снимки контекста, вакансии в отклике и учебного задания не изменяются при выпуске новой версии. Транзакции, блокировки профиля/сущности и уникальные индексы защищают переходы от конкурентных повторов.

### Доступ и минимизация

Пароли хешируются scrypt; в БД хранится SHA-256 случайного 32-байтного токена сессии. Cookie HttpOnly и SameSite=Strict; Secure включается при HTTPS. Сервер проверяет роль, владельца, состояние, согласие и Demo/обычный пул. Подмена user-id заголовком не авторизует запрос. Изменяющие запросы проверяют браузерный Origin; тела и секреты не пишутся в HTTP-журнал.

Подбор не выбирает контактные поля. Работодатель получает разрешённую сводку навыков, а не ответы, ключи или seed. Исследовательские ответы доступны только отдельно назначенному оператору. Локальный rate limiter подходит одной реплике; для нескольких нужен общий счётчик. Логическая изоляция Demo в одной БД не называется физической изоляцией.

# 2. Профиль, опрос и категория

Кандидат регистрируется с email, получает одноразовый код и создаёт собственный профиль. До прохождения проверки профессиональный псевдоним, стек и опыт остаются самоописанием. Для обычного аккаунта новая проверка требует завершённого опроса выбранной специализации; Demo позволяет познакомиться с программой отдельно.

### Резюме и первичный опрос

Структурированное резюме содержит описание, опыт, проекты, образование и HTTP(S)-ссылки. Опрос хранит отрасль, направление и шесть ответов, версию и историю последних завершённых редакций. Backend и Frontend имеют разные вопросы. Рекомендация уровня прозрачна и основана на самооценке, но кандидат выбирает заявляемый уровень самостоятельно.

PDF резюме создаётся серверным PDFKit со встроенными шрифтами. Владелец скачивает его через /api/me/resume/pdf. Самозаявленные и подтверждённые навыки разделены; renderer не принимает email и телефон. Личный экспорт PDF не открывает полный документ работодателям.

### Правила категории

| Правило | Действие системы |
| --- | --- |
| Состав категории | Специализация + подтверждённый грейд Junior, Middle или Senior. |
| Успешная попытка | Порог общей оценки и все критичные критерии выполнены; сохраняется происхождение подтверждения. |
| Неуспех на заявленном уровне | Нет принудительного понижения. Можно выбрать более низкий уровень по правилам повторов. |
| Повтор и повышение | Повтор ограничен 7 днями; повышение - 90 днями. Общий срок выданной попытки - 45 минут. |
| Нижняя или неуспешная попытка | Не освежает дату прежней более высокой категории и не подменяет её навыки. |
| Смена специализации | История сохраняется; новое направление не получает чужие подтверждения автоматически. |

Сырая оценка Junior 100 не эквивалентна Senior 100. Категории основаны на опубликованной проектной рубрике, а не на доказанной статистической эквивалентности человеческой сложности.

### Управление приватностью

Кандидат управляет видимостью профиля и согласием на подбор. Приватность и отсутствие согласия исключают его из каталога, подбора и объяснений; это корректное ограничение доступа, а не потеря релевантного кандидата. Разрешение конкретной компании на контакты хранится отдельно и имеет своё основание и отзыв.

Категорию нельзя получить заполнением резюме, откликом, участием в практике или импортом произвольного ФСП ID. Исследовательский контур также не меняет рабочую категорию.

# 3. Две программы проверки навыков

Активные версии: signal-backend-python-v6 и signal-frontend-typescript-v2. В каждой программе шесть компетенций, три уровня и два собственных смысловых шаблона на компетенцию и уровень: **72 записи реестра**. Перестановка ответов и смена чисел создают формы, но не считаются новыми содержательными шаблонами.

| Backend / Python | Различающиеся сценарии |
| --- | --- |
| API-контракты* | Сохранённый ответ/replay; optimistic write и If-Match. |
| SQL и данные* | Tenant/EXISTS/последняя версия; отсутствие связи/NOT EXISTS/окно. |
| Диагностика | План БД и блокировки; 429, каскад повторов и очередь. |
| Идемпотентность* | Ledger обработанного события; водяной знак и разрыв последовательности. |
| Архитектура | Outbox/consumer/saga; expand-contract и переход данных. |
| Изменение условий | Рестарт или поздний replay; инвалидация кеша и ревизия. |

| Frontend / TypeScript | Различающиеся сценарии |
| --- | --- |
| TypeScript* | Discriminated union; runtime-граница unknown. |
| Состояние* | Неизменяемый reducer; производный фильтр и сумма списка. |
| Производительность | Main thread/worker/передача; waterfall и граница кеша аккаунта. |
| Доступность* | Tab/disabled/возврат фокуса; ошибки формы и live region. |
| Архитектура | Владение состоянием/URL/ревизия; DTO и адаптер модели. |
| Асинхронность | Гонка запросов/unmount; оптимистичная запись и адресный откат. |

Звёздочкой обозначена критичная основа. В новых v6/v2 для Senior дополнительно обязательна архитектура: template version 2. Junior проверяет локальные операции и простые границы, Middle - взаимодействие и устойчивость, Senior - версии, конфликты и восстановление. Это проектная рубрика, не доказательство полного знания языка или человеческой калибровки.

### Задания под роль

Backend имеет контексты API, данных и надёжности; Frontend - продуктовый, платформенный и доступность. Четыре позиции общей основы сохраняются, две прикладные учитывают роль. Можно выбрать свою программу или своё активное приглашение. Грейд приглашения берётся из потребности; чужое приглашение использовать нельзя.

План и пороги общие для грейда. Непокрытые технологии перечислены явно: общий SQL не подтверждает PostgreSQL, Python - FastAPI, TypeScript - React, JavaScript, HTML или CSS.

# 4. Рубрика, банк и устойчивость

Форма состоит из шести заданий: structured, integer, choice, structured, choice, structured. Integer и choice оцениваются 0/100. Structured сравнивается по компонентам на фиксированных местах с равным весом; количество компонентов должно совпасть. Нормализуются Unicode, регистр и пробелы. Свободный текст не оценивается по выдуманному «пониманию смысла».

Итог - округлённое среднее шести критериев. Junior требует 67, Middle/Senior - 83; **все критичные критерии должны быть выполнены на 100**: три в Junior/Middle, четыре в новых Senior v6/v2 с обязательной архитектурой. Частичную или пропущенную архитектуру Senior нельзя компенсировать суммой. Пороги не подбирались по итоговой метрике. Рекомендованные минуты - проектный ориентир, не измеренное время человека.

### Управляемый реестр

Шаблон имеет стабильные ID и версию, программу, грейд, компетенцию, сценарий и состояние доступности. Выдачи считаются по сохранённым templateId, включая истёкшие попытки. При сопоставимых альтернативах выбирается реже встречавшийся сценарий; при равенстве выбор воспроизводим. Нехватка доступных шаблонов возвращает 503, неполная форма не создаётся.

Оператор с локальным доступом к БД отключает шаблон с причиной и аудитом. Отключение и новая выдача сериализованы advisory lock. Активная попытка действует по своему снимку: новые v6/v2 не меняют ключи, critical, категории и результаты прежних kalibr-v4, Backend v5 или Frontend v1. Сохранённая историческая рубрика остаётся действующей для своей выданной попытки.

### Исправление обнаруженной ошибки

Отключить шаблон → зафиксировать дефект и область влияния → проверить независимые эталоны → выпустить новую версию → явно аннулировать затронутую попытку с основанием → предложить повтор. Исходные условия, ответы и оценка сохраняются; correction добавляется в историю. Если профиль ссылался на аннулированную попытку, восстанавливается наивысшее допустимое доказательство того же направления либо подтверждение снимается с объяснением.

Исключение из cooldown действует только на затронутую программу/грейд до замещающего решения. Кандидат не может запросить это исключение через свой API. Скрытого массового пересчёта или переписывания ответов нет.

### Что защищено и что не доказано

Ключи и seed остаются на сервере; есть разные сценарии, параметры, экспозиция и перенос условий. Независимые эталоны, исполнение показанных TypeScript-трасс и adversarial-тесты проверяют оценщик и простые стратегии угадывания. Копирование ответа между формами не даёт гарантированного успеха. Защита от внешнего помощника, LLM, подмены личности и рыночная валидность грейдов не заявляются. Правильное применение изученного метода само по себе не считается обманом.

# 5. Допуск, подбор и объяснение

signal-skills-v1 хранит стабильные ID, контролируемые синонимы и связь с программой. Исходный текст остаётся в БД. Python/python и PostgreSQL/Postgres равнозначны; неизвестное значение остаётся отдельным. SQL не подтверждает PostgreSQL, Python - FastAPI.

### Сначала право показать кандидата

Единый evaluateMatch используется в выдаче, объяснении и при отправке приглашения. Допуск требует того же Demo/обычного пула, согласия на подбор, неприватной видимости, точной специализации, грейда не ниже минимального и каждого обязательного подтверждённого навыка. Каталог использует точный фильтр категории, потребность - минимальный уровень.

Карта покрытия до поиска объясняет непроверяемые технологии. Обязательное требование не становится желательным. Пустая выдача различает отсутствие покрытия, кандидатов и влияние фильтров; изменение условий создаёт новую потребность.

| Общий фактор соответствия потребности | Вес при известной зарплате |
| --- | --- |
| Подтверждённое покрытие обязательных/желательных навыков | 62,5% |
| Формат работы | 18,75% |
| Совместимость зарплатных условий | 12,5% |
| Интервал давности свидетельства | 6,25% |

Общий балл оценивает конкретную потребность и используется между всеми допустимыми профилями. Неизвестная зарплатная база/диапазон имеет `null`, исключается из суммы; известные веса перенормируются. Годовая сумма переводится в месяц только при одинаковой gross/net базе. Интервалы давности: до 30 дней включительно — 1; до 90 включительно — 2/3; менее 180 — 1/3; от 180 или неизвестная дата — 0. Это явная проектная политика, не измеренная утрата навыка человека.

# 5.1. Порядок и происхождение результата

Политика v5/v2 задаёт порядок всего допустимого пула:

1. Общий балл соответствия потребности по убыванию.
2. При одинаковом общем балле — полное связанное действующее свидетельство раньше неизвестного качества. Это приоритет прослеживаемости, а не выдуманная величина отсутствующего результата.
3. В каждом таком срезе формируются очереди по доказанно сопоставимой категории/программе/версии/рубрике. В своей очереди порядок определяется точным результатом проверки плюс ограниченные +3 ФСП, затем NFC-псевдонимом/ID. При одинаковых иных условиях 100 выше 83.
4. Головки разных очередей объединяются по подтверждённому бонусу ФСП и стабильному NFC-псевдониму/ID. Сырые результаты разных банков и грейдов между собой не сравниваются.

Техническое имя/хеш группы устанавливает только принадлежность очереди и никогда не её бизнес-приоритет. Превышение минимального грейда само по себе не является штрафом. Полное происхождение связывает попытку с владельцем, категорией, программой, структурой рубрики и точным временем профиля. Структурная сопоставимость не устанавливает равную человеческую сложность форм.

`rankMatches` подготавливает целую выдачу и назначает позиции; `compareRankedMatches` сравнивает позиции только одной подготовленной выдачи. Нет переключаемого попарного правила, создающего циклы. Production, evaluator и объяснение используют один порядок. Позиция может измениться при изменении текущего допустимого пула.

База остаётся 0–100; `rankingScore` отображает базу плюс бонус ФСП, но не является общей шкалой сырых тестовых результатов. Бонус применяется после общего соответствия и полноты свидетельства; не обходит допуск. Непроверенный ФСП ID не даёт +3.

Объяснение показывает общие факторы, местный результат, источник, дату, статус, позицию и размер пула. Legacy без полной связи: `qualityScore=null/not_measured`; профильный балл не заменяет действующую попытку. Kalibr-v4 без managed template-provenance остаётся неизвестным. Ответы, ключи и seed работодателю не выдаются.

Нижняя/неуспешная попытка не освежает прежнюю категорию; correction исключает отозванную. Зарплата обязательна в рублях; год переводится в месяц только при одной gross/net базе. Подробнее: docs/matching-v5.md. Старый технический порядок v4 сохранён как история, а не переименован в текущую политику.

# 8. Приглашения, вакансии и разрешения

Приватная потребность работодателя хранится отдельно от публичной вакансии. Основной путь начинается с инициативы компании: категория, объяснённое соответствие, приглашение с названием роли, зарплатой и условиями. GET списка не ставит «Просмотрено»: событие фиксируется при открытии конкретного предложения.

### Публичная вакансия и самостоятельный отклик

Создание всегда сохраняет черновик; публикация - отдельное действие. Переходы: draft → published → closed; закрытая запись может публиковаться повторно или архивироваться, черновик - архивироваться. Архив неизменяем. Положительная рублёвая вилка, период и gross/net обязательны. Публичный список исключает черновики и закрытые записи и разделяет Demo/обычный пул.

Перед откликом кандидат видит компанию, условия и состав передачи: имя, email, указанный телефон, псевдоним, специализацию, категорию и письмо. Сервер требует явное согласие, companyId и текущую jobVersion. Смена версии даёт 409. В отклике сохраняется неизменяемый снимок условий; редактирование вакансии влияет только на новые отклики.

Одна пара «кандидат + вакансия» имеет один отклик. Конкурентные запросы возвращают ту же запись. Повтор старого запроса после закрытия не создаёт новый отклик; новый кандидат откликнуться на закрытую вакансию не может. Статусы видны обеим ролям: отправлен, просмотрен, в рассмотрении, отказ, отозван. Отклик не является рекомендацией Signal и не подтверждает навык.

### Единый механизм адресного доступа

signal_contact_grants хранит ровно одно основание: invitation_id или application_id. Источник уникален. Первое принятие/отклик и создание разрешения выполняются в одной транзакции. Повтор никогда не снимает revoked_at. Чтение контактов проверяет конкретную компанию, кандидата, пул и активное основание.

**Отзыв компании закрывает все её существующие основания**, включая приглашения и отклики. Кандидат видит список оснований в «Доступе компаний». Отзыв отклика или контакта приглашения использует тот же механизм. Старое действие не восстанавливает доступ; новое отдельное согласие по новой вакансии может создать только новое основание.

После отзыва работодателю остаются статус и условия вакансии; профессиональный профиль и сопроводительное письмо скрываются. Запрос, выигравший блокировку до отзыва, может завершиться; последующие чтения запрещены. Уже полученные внешним адресатом копии Signal удалить с его устройств не может.

Проверки: чужая компания, несколько оснований одной компании, конкурентный повтор, отзыв и повтор после отзыва, новая передача без оживления старых оснований. Протокол - outputs/verification/opportunities-integration.json.

# 9. Регулярная короткая практика

Компания создаёт самостоятельную учебную ситуацию на вымышленных данных: компетенция, ожидаемый ответ, 5-45 минут, рубрика 1-6 критериев, срок ответа 1-7 дней, период 7-90 дней. Требуется подтверждение учебного назначения: без бесплатной производственной работы, доступа к системам и персональных данных. Этот флажок не является проведённой внешней модерацией компании.

Кандидат отдельно разрешает предложения. Работодатель видит только согласившихся на практику кандидатов своего пула, с подтверждённой категорией, согласием на подбор и неприватным профилем. Появление учебного задания не обходит обязательную проверку категории.

### Полный цикл

Предложено → принято / отказ → ответ отправлен → оценено. При принятии кандидат отдельно разрешает компании прочитать и оценить ответ. Контакты не передаются. Отказ относится к одному предложению; остановка программы прекращает будущие. Глобальное отключение останавливает подписки и открытые предложения. Повторное включение не оживляет старые подписки без отдельного действия кандидата.

Снимок условий и рубрики неизменяем. Ответ после отправки нельзя заменить: тот же повтор идемпотентен, другой текст даёт 409. Сервер отклоняет приём и отправку после срока. Оценка требует все критерии без дублей, допустимые баллы и комментарии. Сохранённая оценка неизменяема; тот же повтор возвращает её.

### Периодичность существует на сервере

Сохранённые next_due_at и last_offered_at переживают перезапуск. Обработчик запускается со стартом API и раз в минуту. Выдача и продвижение даты - одна транзакция; уникальность пары «подписка + плановая дата» и блокировка кандидата защищают от двух workers.

Глобальный лимит: не более одного нового предложения за 7 дней от всех компаний и одного незавершённого одновременно. После простоя нет пачки пропущенных задач: новая дата считается от фактической выдачи. Проход страницами по сроку и ID пропускает недоступные подписки и даёт очередь давно ожидающим программам.

### Самостоятельное свидетельство

Результат хранит компанию-автора, оценивший аккаунт, компетенцию, версию, баллы, комментарии и серверную дату. Свежесть относится к этому свидетельству; категория и дата основного подтверждения не меняются. Компания видит только ответы своих заданий. Внешняя краткая сводка появляется лишь по отдельному разрешению кандидата; ответы и ID оценщика туда не входят.

Отзыв закрывает ответ/результат компании, снимает внешнюю сводку и останавливает подписку; собственная история кандидата сохраняется. Регрессия с управляемыми часами проверяет неделю, срок, opt-out, возобновление и конкуренцию только на захваченных синтетических ID. Через HTTP нельзя передать тестовую дату или обойти расписание.

# 10. ФСП, доверие и будущая ATS

### Реализованная связь с ФСП ID

Официальный API и структура реестра для трека не предоставлены. Кандидат может сохранить собственный ID с отдельным согласием. Состояния: unlinked, pending, connected_demo, unavailable. Обычный ID получает pending без достижений и бонуса. Лишь зарезервированный ID в Demo при DEMO_MODE=true возвращает явно синтетическую историю. Отсутствие ФСП не исключает кандидата.

Изменение связи и флага истории атомарно. Повтор одинакового ввода не меняет даты согласия/импорта. Отзыв удаляет ID и импортированные достижения, снимает влияние на ранжирование и оставляет минимальные отметки согласия. Ошибка провайдера не подменяется успехом.

### Проект реального подключения

Предлагается OIDC Authorization Code + PKCE, state/nonce, проверка issuer, audience, подписи, срока и одноразовости. Keycloak совместим с этой границей. Владение ID подтверждается провайдером; pending не даёт права автоматически привязать чужой ID. Импорт минимальных событий/результатов имеет отдельное согласие, идемпотентность, таймауты и даты источника. Реальные endpoint и поля определяются будущим официальным контрактом. Одна смена переменной не превращает Demo в интеграцию.

### Антифейк: архитектурная проработка

Подтверждённый email не означает проверенную компанию или публикацию. Предложены отдельные company_verifications, moderation_cases/events, employer_restrictions и invitation_rate_buckets. Владелец подаёт сведения, модератор проверяет, другой модератор рассматривает апелляцию. Журнал содержит причины и сроки; документы закрыты, данные жалобщика компании не выдаются.

Проектные состояния компании: unreviewed → pending → verified/rejected → expired/suspended. Жалоба может временно ограничить новые действия; история сохраняется. Предложенные дневные лимиты 20/100 являются настройкой будущего пилота, не внедрённой проверкой. Спецификация - docs/trust-and-ats.md.

### ATS: архитектура и локальный контракт

Отдельный ats_export grant относится к компании, подключению, полям и основанию. Обычное раскрытие контактов не даёт безусловного разрешения на любую ATS. Outbox хранит event_id, неизменяемое тело, lease, попытки и аудит. Idempotency-Key равен event_id; 429/5xx/timeout повторяются с backoff/jitter и Retry-After, 4xx ведут в dead-letter, 401 допускает одно обновление токена.

Перед отправкой повторно проверяется согласие; отзыв отменяет неотправленные события. Уже доставленные копии удалить гарантированно нельзя. Планируются OAuth2/отзываемый ключ, HTTPS, allowlist URL и HMAC webhook. Локальный синтетический пример проверяет минимизацию, повторы и отзыв в памяти, без внешних передач. Работающей ATS-интеграции и проведённой модерации юридических лиц нет.

# 11.1. Ответы, ошибки и границы ID

200/201 - выполненное действие; 400 - некорректные поля/согласие; 401 - нет сессии; 403 - роль или доступ запрещены; 404 - ресурс не найден/недоступен в данном пуле; 409 - конфликт версии или перехода; 429 - локальный лимит; 503 - недоступное покрытие банка/сервис. Успешный старый повтор не означает новое согласие.

QA-04 ограничивает PostgreSQL `serial/integer` ID диапазоном **1…2147483647**: числа в JSON, канонические десятичные строки в URL; дробные/переполненные/некорректные значения отклоняются до SQL. UUID/bigint и строковые ID программ не подменяются этой политикой. Локальные unit/Express/typecheck и 130 запросов к изолированному приложению прошли; независимая приёмка реального image55a5 завершена в составе 60/60 групп.

Сервер не доверяет ID из браузера, проверяет права и переходы. Неизвестное состояние не считается успешным. ATS/модерация остаются архитектурой, не работающим публичным API.

# 12. Компоненты, версии и запуск

Версии пакетов берутся из pnpm-lock.yaml, а не только из диапазонов package.json. Полный lockfile входит в исходный архив. Стандартные библиотеки используются по их лицензиям; лицензии шрифтов включены в поставку.

{{dependency_table}}

### Локальная разработка

Требуются Node.js 24, pnpm 11.25.0 и Docker Compose. Из папки исходников выполняются команды:

```powershell
node scripts/setup-env.mjs
pnpm install --frozen-lockfile
docker compose up -d db mail
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Веб: http://127.0.0.1:4310, API: 4312, PostgreSQL: 55433, локальная почта: http://127.0.0.1:8026. После регистрации код читается в Mailpit; внешнему адресату он не доставляется. «Вход» вверху открывает форму; Demo внутри неё подставляет данные выбранной роли и создаёт отдельную синтетическую сессию.

### Весь стенд в контейнерах

```powershell
node scripts/setup-env.mjs
docker compose --profile full up -d --build
```

Остановите pnpm dev перед использованием того же порта 4310. Контейнер сам применит миграции и идемпотентный seed; дождитесь health/Server listening. docker compose down сохраняет том БД; down -v удаляет данные и для обновления не нужен. Секреты создаются локально, .env не входит в архив.

### Внешний запуск

Для внешнего запуска нужны HTTPS, PUBLIC_URL, постоянный случайный секрет, закрытая БД и проверенные backup. Обычного .env недостаточно: compose.yaml явно задаёт Demo, Mailpit и localhost. SMTP Nodemailer: аутентификация, TLS/сертификат, таймауты, запрет внешних URL/файлов. MAIL_TRANSPORT=smtp, SMTP_HOST/PORT/USER/PASSWORD, MAIL_FROM. Внешняя доставка не проверена; локально Mailpit.

### Передача и следующие внешние действия

Комплект: исходный ZIP, PDF, презентация, видео, инструкции/лицензии и SHA-256 manifest. Видео Signal-Demo.mp4: **138 секунд / 21 сцена**, монтаж локальных UI-кадров синтетических обычных аккаунтов без озвучки. Проверены decode, все сцены/подписи и UI-пиксели. Запись на image55a5 сохраняет происхождение; одинаковый frontend и независимые 20 групп подтверждают совместимость с imagef5c067, повторная съёмка не заявляется. Обычный путь: регистрация, локальное email-подтверждение обеих ролей, опрос, проверка, подбор, приглашение, контакты и отклик. Собственные проверочные данные очищены.

Локальный адрес не доступен жюри извне. Чистый запуск точного запечатанного исходного ZIP передаётся отдельным companion-протоколом с SHA архива; после проверки исходный ZIP и этот PDF не перепаковываются. Текущий документ не выдаёт этот будущий post-seal результат за уже выполненное измерение.
