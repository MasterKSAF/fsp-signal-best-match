# Связь с ФСП ID и реестром

[Письменные ответы ФСП](official-written-qa-20261007.md), A1/B1, подтверждают усиление внутри подтверждённой категории без замены теста и равнозначность спортивных дисциплин. Релевантность дисциплины специальности — факультативная идея, а не обязательная иерархия. Ответы не предоставляют API реестра, механизм владения ФСП ID или параметры почты: эти вопросы остаются открытыми. Вес участия/приза/победы и защита доверия к источнику остаются решениями Signal; ответ не подтверждает существование внешнего подключения.

## Что реализовано

В паспорте кандидата доступен раздел «Спортивные достижения». Пользователь может сохранить ФСП ID с отдельным согласием, посмотреть состояние связи и отозвать согласие. Без ФСП ID и спортивной истории доступны профиль, проверка навыков, подтверждение категории и приглашения.

Официальные адреса API, схема реестра и параметры OIDC не предоставлены в материалах задания. Поэтому ввод идентификатора **не подтверждает владение им**, не запрашивает чужие данные и не даёт бонуса. В обычном аккаунте ID сохраняется как `pending`; реальный реестр не вызывается. Идентификаторы пока не уникальны между пользователями: неподтверждённая заявка не может заблокировать чужой ID.

В аккаунте с примерами при `DEMO_MODE=true` доступен один заранее известный ID `FSP-DEMO-2026`. Кнопка «Заполнить пример» не принимает согласие за пользователя: галочку нужно поставить отдельно. Текущий `signal-fsp-example-v2` возвращает три явно вымышленные записи с исходами участия, призового места и победы; сохранённая v1 читается по своей версии. Другие идентификаторы не открывают историю. Обычный аккаунт не может импортировать пример даже при включённом общем режиме демонстрации.

| Состояние | Что видит кандидат | Влияние на подбор |
| --- | --- | --- |
| `unlinked` | ФСП ID не добавлен | Нет |
| `pending` | ID сохранён, ожидает подключения | Нет |
| `connected_demo` | История на примере, каждое соревнование помечено | Ограниченный лучший доверенный исход, только внутри подтверждённой категории разрешённого демопула |
| `unavailable` | Сведения временно недоступны, основные функции работают | Новые неподтверждённые сведения не учитываются |

Фоновый набор демонстрационных кандидатов содержит собственные синтетические сведения. Эти записи не являются импортом из ФСП и не смешиваются с реальными аккаунтами. Сам ID или legacy-флаг `hasFspHistory` не даёт эффекта: действующая политика проверяет текущую связь, согласие, происхождение, версию и явный исход. Подробнее — [категории и результаты ФСП](matching-fsp-category-0.6.0.md).

## Контракт и хранение

- `GET /api/me/fsp-connection` — собственная связь, список достижений и временные отметки. Нужна сессия подтверждённого кандидата; работодатель получает `403`.
- `PUT /api/me/fsp-connection` с `{ "fspId": "…", "consentImport": true }` — сохранить/заменить ID. Дополнительные поля, включая попытку передать `verified`, отклоняются. Формат ID ограничен локально длиной 100 символов и ASCII-буквами, цифрами, `.`, `_`, `:`, `-`; это не объявляется официальным форматом ФСП.
- `DELETE /api/me/fsp-connection` — отозвать согласие и удалить идентификатор, импортированные достижения и источник из профиля. Возвращает `unlinked`; повторный вызов не создаёт новых событий.

Таблица `signal_fsp_connections` имеет одну строку на пользователя: ID, состояние, версия и дата согласия, даты запроса, проверки и импорта, источник, версия адаптера, достижения, дата отзыва и безопасный код ошибки. При отзыве сохраняются только минимальные отметки согласия/отзыва; ID и достижения очищаются. Таблица удаляется каскадно с аккаунтом.

Связь и `hasFspHistory` обновляются в одной транзакции с блокировкой профиля. Замена примера обычным ID и отвязывание сразу снимают флаг истории. Повторный одинаковый `PUT` сохраняет даты импорта и согласия. Отзыв не затрагивает результаты проверки навыков и контактные согласия работодателям. Защита сессии, роли и браузерного Origin применяется общим middleware и проверяется в маршруте. Ответы имеют `Cache-Control: no-store`; ID и содержимое тела не выводятся в HTTP-журнал.

OpenAPI-фрагмент: `docs/contracts/fsp-openapi.yaml`. Интерфейс провайдера: `FspRegistryProvider.resolve(fspId, context)` в `artifacts/api-server/src/lib/fsp-provider.ts`. Обёртка `resolveFspSafely` переводит исключения, неполные ответы и недопустимые claims в `unavailable`, очищая достижения и не раскрывая внутреннюю ошибку.

## Проектируемое подключение реального реестра

Ниже проект интеграции, **не реализованное подключение и не описание существующего API ФСП**. Он уточняется после получения документации, доступа и согласования состава данных.

1. Signal создаёт одноразовый запрос связи, привязанный к локальной сессии. Внешний вход — OIDC Authorization Code с PKCE, `state` и `nonce`; совместимый Keycloak может выступать провайдером идентификации. Callback проверяет подпись, issuer, audience, срок, одноразовость и совпадение состояния. Идентификатор берётся из подтверждённого claim, а не из формы.
2. После проверки владения кандидат видит доступные категории сведений и даёт новое согласие на импорт. Старый `pending` сам по себе не разрешает автоматически связать произвольный ID. Только после успешной проверки возможна уникальная связь `(issuer, subject)` с аккаунтом.
3. Серверный адаптер получает минимальный набор: внешний ID/subject, события, результаты, статус/разряд при наличии, внешний ID записи, дату обновления и источник. Точный endpoint и поля задаются официальным контрактом, а не угадываются. Ключи и токены хранятся на сервере вне репозитория, не передаются браузеру.
4. Импорт ограничен таймаутом, объёмом, допустимыми полями и частотой. Ключ идемпотентности — подтверждённый subject, ID события и версия/дата изменения. Фиксируются время импорта и время обновления источника. Обновление снимка и признаков подбора атомарно; пустая подтверждённая история — нормальный результат, без бонуса.
5. При сбое отображается недоступность. Неудачный импорт не создаёт достижений и не меняет категорию проверки навыков. Правила срока годности ранее подтверждённой истории и повторных запросов согласуются с реестром; просроченные данные не выдаются за актуальные.
6. При отзыве отключаются запланированные обновления, удаляются импортированные сведения и влияние на ранжирование; токены отзываются у провайдера, если его протокол поддерживает revocation. Остаётся минимальный аудит согласия. Новая связь требует нового подтверждения.

Существующий адаптер намеренно принимает только локальный пример. Для production-провайдера потребуются отдельное состояние подтверждённой реальной связи, OIDC callback, расширение проверки доверия и миграция модели. Одной сменой переменной окружения получить реальную интеграцию нельзя.

## Проверка

`tests/fsp-provider.test.ts` проверяет строгий ввод и явное согласие, запрет примера для реальных/отключённых аккаунтов, отсутствие истории и бонуса у произвольного ID, изоляцию копий примера, необходимость доверенного источника, очистку claims при замене ID и безопасное поведение при сбое/повреждённом ответе адаптера. Сетевые обращения для этих тестов не нужны.

Сквозной сценарий текущей v2: добавить пример с согласием → увидеть три помеченных исхода → обновить страницу → повторить сохранение без смены временных отметок → заменить ID произвольным значением и проверить пустую историю → отвязать → повторно отвязать. Отдельно проверяются `401` без сессии и `403` для работодателя. Эта редакционная карта не является новым выполненным прогоном; старые протоколы v1 сохраняют свои исходные данные.
