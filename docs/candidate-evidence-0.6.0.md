# Реестр подтверждений кандидата — Signal 0.6.0

## Политика и границы

Подтверждение критерия принадлежит аккаунту, а не отдельной копии резюме. Источник идентифицируется тройкой `attemptId:criterionId:canonicalSkillId`. Копирование, переименование, смена основного резюме и создание нового совместимого резюме не создают новое наблюдение, дату проверки или право обхода повторной попытки. Удаление исходного резюме оставляет источник в истории; удалённый документ не становится действующей целью применения и не восстанавливается чтением реестра.

Применимость рассчитывает существующий общий `getResumeQualification`; владелец получает дополнительное объяснение каждого критерия через `qualification.applicability`. Реестр и интерфейс не определяют совместимость самостоятельно. `applied` означает допустимость исходного критерия в контексте резюме, а `selected` — выбор этого конкретного источника для текущего публичного навыка. Совместимый более ранний или менее высокий источник может остаться в истории с причиной `superseded`.

Результат 100% отдельного критерия уровня Middle не означает подтверждённый грейд Middle. Грейд по-прежнему требует полного результата одной программы и выполнения её критичных требований. Частичные результаты не суммируются в новый грейд. Подтверждённые Backend Middle и Frontend Junior одного аккаунта остаются независимыми.

## Версионированная совместимость

Версия политики: `signal-evidence-compatibility-v1`. В коде зафиксировано 90 правил собственного исходного критерия: пять распознаваемых исходных версий × шесть семейств × три уровня. Это правила сохранения прежнего источника в собственной программе, а не заявление о равной сложности старой и новой формы.

| Программа | Распознаваемые исходные версии | Разрешённое применение |
| --- | --- | --- |
| Backend / Python | `kalibr-backend-python-v4`, `signal-backend-python-v5`, `signal-backend-python-v6` | Исходный проверенный критерий и уровень Backend / Python |
| Frontend / TypeScript | `signal-frontend-typescript-v1`, `signal-frontend-typescript-v2` | Исходный проверенный критерий и уровень Frontend / TypeScript |

Текущие банки не содержат содержательно обоснованных общих критериев между Backend и Frontend. Поэтому межпрограммных правил нет: SQL сохраняется в аккаунте, но не становится подтверждением Frontend и не переносит весь Backend-грейд. Python не отождествляется с TypeScript, SQL — с PostgreSQL, надёжность повтора событий — с асинхронным состоянием интерфейса. Для неподдерживаемого направления, неизвестной версии или критерия применяется отказ с объяснением и следующим шагом.

Сохранённые v4/v5 используют исходную рубрику, дату и уровень. Они не объявляются экзаменом v6. Новый общий критерий можно разрешить только после содержательной проверки с новым явным правилом и версией политики. Совпадения названий навыков недостаточно. Матрица не меняет политику сравнения качества форм, грейд, сроки 7/90 дней или назначение задания компании.

## API и приватность

Новый additive endpoint: `GET /api/me/evidence/registry`. Существующий `GET /api/me/evidence?resumeId=…` и его паспорт навыков сохранены. Доступ: текущая сессия кандидата-владельца, `401` без неё и `403` работодателю. Любые query selectors, включая `userId` и `resumeId`, отклоняются с `400`. Ответ: `Cache-Control: no-store, private`.

Объекты ответа:

- `matrixVersion` — версия политики.
- `resumes[]` — только действующие собственные документы: id, revision, title, specialization, visibility, isPrimary и вычисленный verifiedGrade.
- `evidence[]` — исходные критерии: id, skill/canonicalSkillId, criterion/criterionId, date, sourceType, purpose, attemptId, originalResumeId, programId/programVersion, grade уровня критерия, result, status, limitation, correction и applications.
- `applications[]` — resumeId, applied, selected, reason/reasonCode, compatibilityRuleId и nextStep. Объяснения получены из общего квалификатора.
- `historicalQualifications[]` — ограниченные прежние итоги без полной версии и критериев. Они не преобразуются в вымышленные индивидуальные доказательства. Одинаковая историческая запись в копиях дедуплицируется.

Чтение использует одну транзакцию `repeatable read`, `accessMode: read only`, чтобы источник, исправление и состояние документов были согласованы. Владелец видит скрытые собственные документы. Ответ не включает ответы экзамена, oracles, тела заданий, контактные поля, операторов исправления, фотографии или внутренние подписи пула. Коррекции выбираются с owner join; отозванный источник сохраняет исходный результат и дату, но ни в одном резюме больше не применяется. Задание компании не является квалификационным источником.

Под общей блокировкой владельца пересчёт изменившейся квалификации согласует привязанные задания компаний. Скрытие, удаление, отзыв consentMatching или смена IT-направления отзывают связанные подписки/предложения; переключение основного резюме не переносит их на другой документ. Тела и результаты прежних заданий сохраняют свою исходную привязку. Конкретный механизм подписки и его HTTP-проверки описывает владелец п.4.

## Компонент интерфейса

Изолированный `CandidateEvidenceRegistry` находится в `artifacts/fsp-signal/src/components/candidate-evidence-registry.tsx`, CSS импортируется самим компонентом. Он не выполняет запросы и не меняет политику совместимости.

```tsx
<CandidateEvidenceRegistry
  catalog={registryQuery.data}
  loading={registryQuery.isLoading}
  error={registryQuery.error?.message}
  selectedResumeId={selectedResumeId}
  onSelectResume={selectResume}
  onStartAssessment={resumeId => navigateToAssessment(resumeId)}
  onRetry={() => registryQuery.refetch()}
/>
```

Родитель должен включать текущий аккаунт в query key, очищать данные при смене сессии и инвалидировать реестр после изменения документов/завершения проверки/отзыва. Компонент показывает общую историю, применимость к выбранному документу, исходный проверенный критерий, источник и версию, исходную дату и причину неприменения. Чип «Критерий Middle» явно отделён от подтверждённого грейда документа. Раскрываемый список содержит все действующие собственные резюме. Отозванные и ограниченные исторические записи показываются без выдачи за новые подтверждения.

## Поля редактора резюме и выбора документа

В `candidate-resume.tsx` все обёртки полей используют общий `FormField`: явный label/id, связанные подсказки, вертикальная компоновка длинных вопросов/текста/тегов. `multi-resume.tsx` применяет тот же контроль к переключателю, созданию документа и загрузке фото. Поля опыта, образования, описаний и контактов не превращаются в доверенные словари.

| Поле | Контрол и источник вариантов | Поиск | Свой текст | Сохранение |
| --- | --- | --- | --- | --- |
| Должность в опыте, роль проекта | DictionaryCombobox, локальный ROLE_OPTIONS | Да | Да | Исходный текст в experience.role / projects.role |
| Личные навыки | DictionaryTags, локальный SOFT_SKILL_OPTIONS, максимум 20 | Да | Да | Массив softSkills, без отдельного CSV-черновика |
| Предметная область | DictionaryCombobox, локальный DOMAIN_OPTIONS | Да | Да | Прежнее questionnaire.industry; направление экзамена не меняет |
| IT-направление опроса | Readonly | Нет | Нет | Следует за программой выбранного резюме |
| IT-направление при создании | Простой select двух поддерживаемых программ | Нет | Нет | specialization, отдельный документ без контактов/согласий по умолчанию |
| Название нового резюме | DictionaryCombobox с примерами должностей | Да | Да | Отдельное title, не новая программа и не грейд |
| Активное резюме | Select собственных действующих документов | Нет | Нет | Явный resumeId |
| Ответы первичного опроса | Select существующей шкалы | Нет | Нет | Прежние ключи questionnaire.answers |
| Компания, проект, образование, описания, ссылки | Input/textarea/date/url | Нет | Да | Прежние поля DTO и их пределы |
| Фото профиля | Native file input | Нет | Нет | Общая фотография аккаунта с серверной проверкой формата/размера |

Сохранение редактора и действия с документом инвалидируют owner query `candidate-evidence-registry`. Изменение документа в другой вкладке сохраняет прежний черновик и ревизию: контролы справочников не ослабляют существующий отказ 409. Общие клавиатурные правила/буфер вставки/ограничения справочников и анимаций принадлежат переиспользуемым компонентам координатора; окончательный браузерный протокол — отдельная проверка.
