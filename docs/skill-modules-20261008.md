## Реестр и содержание

Новые выдачи: банк `signal-skills-2026-10-v3`, рубрика `six-competencies-critical-5of6-middle-outcomes-v3`. Для `frontend-engineering:Middle:state-model:s1` templateVersion=3; остальные шаблоны сохраняют templateVersion=2. Подготовлены шесть самостоятельных модулей, каждый с Junior и Middle. Senior показан как неподготовленный, сервер возвращает422, без чужого экзамена по fallback. Сохранённые программы v1/v2, их условия, ключи и исходные рубрики остаются воспроизводимыми; уже выданные формы не перестраиваются по новому банку.

| Модуль | Шесть проверяемых областей |
| --- | --- |
| Python | Коллекции/ссылки; итерация; функции/область видимости; исключения; ресурсы; внешние данные |

| Frontend engineering | State model; доступность; производительность; async UI; архитектура; интеграционный сценарий |

Это 108 общих базовых content families и 216 версионированных ячеек «семейство × Junior/Middle», **не 216 независимых сюжетов**. На базовую область подготовлены три сценария с разным ходом рассуждения. В v2 добавлены 36 самостоятельных проверяемых Middle requirements: шесть на каждый модуль. Каждый дополнительный requirement применяется ко всем трём соответствующим базовым семьям, поэтому они не объявляются 108 новыми продвинутыми сюжетами. Seed, перестановка ответа и число не считаются самостоятельными заданиями.

Junior проверяет результат в заданном локальном контракте и понимание основ. **Каждая** Middle форма v2 содержит части A и B во всех шести заданиях, включая оба критических. Часть B проверяет дополнительное требование; знание только Junior/A не подтверждает компетенцию. Оба результата должны совпасть с сохранёнными ключами. Формат одного ответа: `результат A ; результат B`; трассы внутри частей разделяются `|`, варианты выбора явно нумеруются. `levelCriteria`, `middleOutcome`, `levelRequirementId` открывают проверяемые требования до начала, а `levelCoverage` сохраняет проверенное покрытие в решении. Middle proof v2 без такого покрытия не принимается матрицей.

Например: Python — deepcopy с внутренним alias и отдельной исходной структурой, `ExitStack` и изменение исключения после suppression; SQL — fan-out двух JOIN, weighted aggregation, write skew, RANGE/ROWS с peers, scope ключа + неизменный payload hash + атомарный receipt; React — functional/replacement queue с устаревшим callback, граница parent key, серверный baseline при более новом локальном draft. Backend critical дополнительно различает receipt namespaces `(principal, action, key)`, включая двух клиентов и разные операции; безопасность задаёт точку сериализации экспорта/отзыва. Frontend проверяет DAG critical path и разделяет Worker latency/responsiveness, связанные optimistic updates и границу аккаунта при позднем ответе.

В SQL constraints:s1 v2 оба tenant_id обязательны и система многопользовательская: глобальный event_id обязан отвергать `(1,7)`/`(2,7)` как повтор, локальный обязан принимать их как независимые события. Поэтому два UNIQUE больше не равноправны. Старая single-tenant формулировка v1 и её oracle сохранены как история; она не используется в новых выдачах.

Разделение сложности является собственной методикой команды и ещё требует внешней человеческой калибровки. Проверка SQL не подтверждает PostgreSQL; TypeScript не подтверждает React; узкий прежний критерий не становится полным подтверждением Python. Framework-навыки и неподготовленные стеки можно заявлять без фиктивной сертификации.

В попытке шесть заданий, по одному на область, 30 минут. Минимум пять верных из шести (83 после округления) и оба критических критерия: фундаментальный контракт первой области + граница/интеграция последней. Недостаток критического критерия нельзя компенсировать баллами. Оценка детерминирована сохранёнными oracle/policy/cases; свободное эссе или LLM-вердикт не используются. Ответы на трассировку вводятся по явному контракту через `|`, нормализуются Unicode/внешние пробелы. В новом integer-формате v2 эквивалентные записи +010/10 принимаются; десятичная/экспоненциальная запись не является предусмотренной integer-записью. Сохранённая v1 продолжает точное сравнение по своей политике, старые результаты не переоцениваются. Критерии для каждой программы доступны до начала. Сам выбор ячейки не выдаёт попытку.

## Общая категория

Версия обязательной матрицы `signal-category-competency-matrix-v1`:

| Специализация | Обязательное покрытие на подтверждаемый уровень |
| --- | --- |
| Backend / Python | Поддержанный объявленный язык Python **или** TypeScript + SQL + Backend engineering |
| Frontend / TypeScript | Объявленный React + TypeScript + Frontend engineering |

У всех трёх самостоятельных свидетельств уровень не ниже проверяемой категории. Общие инженерные модули обеспечивают одинаковые обязательные требования к альтернативам серверного языка. Другой язык/фреймворк не получает подтверждение по совпадению слова Backend/Frontend. Совместимость ограничена тем же навыком/программой: Middle покрывает Junior; SQL не переносится в PostgreSQL. При двух поддержанных языках достаточно одного подходящего — дополнительные навыки не понижают категорию.

Общая категория — высшая закрытая строка Junior/Middle, ограниченная выбранной кандидатом целью. Изменение цели само не создаёт доказательств. Удаление необязательного навыка не уменьшает обязательную матрицу. Явный переход с неподдержанного стека к подтверждённому отражает изменение стека, не переименование старой квалификации. При цели Senior доступны точные причины отсутствия его программы; закрытый Junior сохраняется.

Свидетельство принадлежит аккаунту, удаление/скрытие резюме его не уничтожает. Резюме применяет релевантные свидетельства по своему стеку/специализации. Сертификат категории хранит неизменяемый снимок нескольких evidence IDs, исходные даты/версии, матрицу, специализацию, цель и подтверждённый уровень. Поля `verifiedScore` и `qualificationAttemptId` для новой категории — `null`: среднее разных шкал и фиктивная монолитная попытка не создаются. Подбор признаёт полную матрицу как подтверждение категории без выдуманного общего балла. Уровень требования отдельного навыка проверяется отдельно; прежние требования без уровня не получают новый минимум.

Историческая более высокая категория остаётся по прежнему основанию/дате и обозначена отдельно. Новые skill-level ей не приписываются. Модульные proofs v1 также сохраняют исходные версии/даты/решения: им не приписываются дополнительные Middle outcomes v2. Свежая проекция matching явно указывает исходный scope v1. Старую активную попытку можно открыть по исходному `?attempt=`, новую — по `?moduleAttempt=`. Старые правила повтора продолжают действовать для старых маршрутов.

Соответствие B5/B9/B12/B13: категория подтверждается объективными проверками, а не стажем или вакансией; самостоятельный интеграционный модуль проверяет взаимосвязанные решения, не набор случайных справочных фактов. Модульная архитектура — наша проектная интерпретация, **не отдельное согласование этой архитектуры заказчиком**. Подтверждение ФСП не повышает категорию и остаётся преимуществом внутри подходящей категории.

## Выдача, ротация и коррекции

Новая политика — настройки продукта, не требование ФСП: повтор того же skill-level через 24 часа после сдачи; максимум две новые выдачи навыка за скользящие 24 часа **между уровнями/резюме**, максимум восемь всех новых модульных проверок аккаунта. Истёкшие/брошенные выдачи учитываются. Разные навыки не наследуют старое семидневное ожидание. Точное время и причина ограничения показаны до выдачи. Ровно на границе времени ограничение снимается.

Атомарная блокировка аккаунта обеспечивает один результат параллельных стартов. Действительная попытка восстанавливается без нового seed, комплекта, лимита или показов. Серверные ответы имеют revision; конфликт требует явного выбора. Клиент хранит собственный локальный черновик по аккаунту/попытке и восстанавливает совместимую версию; чужая серверная версия не перезаписывается молча. Таймер определяется сохранённым expiresAt и не зависит от темы/анимаций.

Выбор приоритизирует меньше показанные аккаунту сценарии, затем реже показанные всему изолированному контуру за 30 дней, затем серверный tie-break. Семейство `skill-content-v1:<skill>:<competency>:sN` объединяет эквивалентный базовый контент Junior/Middle и старых/новых программ: переход уровня или версии не обнуляет показ. Все 108 families учитываются совместно; дополнительные требования Middle не смешивают разные навыки. Показ записывается вместе с попыткой, уникален для attempt/template. Учёт персональных показов включает незавершённые формы и все резюме. Одно короткое глобальное locking-окно защищает балансировку параллельных выдач. Старые формы не меняются; учёт показов управляет следующей выдачей и не наказывает освоение метода.

Отключение повторно использует `signal_bank_template_overrides`/журнал `signal_bank_audit` и тот же операторский CLI. Блокировка существующего управления банком исключает гонку с новой выдачей. Отключённые сценарии больше не выдаются; при отсутствии покрытия возвращается 503, вместо подмены компетенции. Исходные снимки уже выданной попытки сохраняются.

Команды `inventory`, `disable`, `enable` принимают новые стабильные template IDs. `annul-skill --evidence ID --operator NAME --reason TEXT` требует явного основания; ID относится к **skill evidence**, не старой попытке. В отдельной append-only коррекции сохранён исходный decision, причина и дата. Текущие зависимые резюме пересчитываются, прежние категории/попытки остаются в истории. Владелец видит отзыв и причину. Подозрение, IP или общий компьютер не вызывают автоматический отзыв.

Подтверждающее уточнение реализовано отдельно как явно тренировочный `/me/skill-training/changed-condition`: проверяемый результат изменённого условия, без влияния на skill evidence/grade. Скрытого седьмого задания и автоматического обвинения нет. Обучающие вопросы отделены от рабочих снимков.

Экспертная сложность, человеческая эквивалентность вариантов, предсказание найма и спортивный разряд не доказаны. Senior намеренно не сертифицируется.

## Интеграция и миграция

Аддитивная миграция `0010_skill_modules.sql`: attempts, exposures, evidence, corrections, category receipts. Переписывание/переименование исторических записей отсутствует. Новый DB-export зарегистрирован координатором; router `signal-skill-modules.ts` подключён в общий router. Основные helpers: `getSkillQualification`, `loadSkillQualificationInputs`, `getCurrentResumeWorkspaceQualification`, `moduleMatchEvidence`; root интегрировал свежие account proofs в matching/catalog и обновил контракты.

Рабочий UI: `/candidate/passport`, `/candidate/kalibr`; реальные API `/api/me/skill-matrix?resumeId=…`, `/api/me/skill-target`, `/api/me/skill-attempts`, `/api/me/skill-attempts/:id/answers|submit`. Формы/ключи/seed — только на сервере. Артефакты проверки: `outputs/verification/candidate-workspace-skill-matrix-20261008/`. Credentials собственных акторов находятся только в приватном manifest компьютера; их нет в документации/репозитории.
